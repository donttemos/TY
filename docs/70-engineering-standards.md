# 编码 / Git / PR 规范

> 版本 v0.2 ｜ 状态：草案 ｜ 适用范围：本仓库全部代码与文档 ｜ 更新：2026-10-09
>
> 配套：[完成定义（DoD）](./10-acceptance-criteria.md) ｜ [测试用例](./50-test-cases.md) ｜ PR 模板：`.github/PULL_REQUEST_TEMPLATE.md`

## 1. 编码规范

### 1.1 TypeScript

| 项 | 规则 |
|---|---|
| 严格模式 | `strict: true`；框架包禁止 `any`，用 `unknown` + 收窄 |
| 命名 | 类/接口/类型 `PascalCase`；变量/函数 `camelCase`；常量 `UPPER_SNAKE`；文件名 `kebab-case` |
| 导出 | 每个包的对外 API 从 `index.ts` 统一导出，禁止深路径引用内部文件 |
| 空值 | 禁止非空断言 `!`（除测试与已校验场景）；优先可选链与显式判断 |
| 异步 | 统一 `async/await`，禁止裸 Promise 链混用；所有 I/O 必须有超时 |
| 错误 | 抛框架定义的业务异常（带错误码），禁止 `throw new Error('字符串')` 裸抛 |
| 注释 | **一律中文**，每个文件必须有文件头（含作者与日期）；对外 API 必须有 JSDoc。详见 §1.6 |
| 依赖 | 禁止在业务模块直接 `import` 驱动实现（mysql/redis/…），只能依赖接口 token |

### 1.2 分层与目录

```
apps/<app>/modules/<业务模块>/
  ├─ <module>.controller.ts   # 只做参数校验与响应组装
  ├─ <module>.service.ts      # 业务编排、事务边界
  ├─ <module>.repository.ts   # 数据访问，实现框架 Repository 接口
  ├─ dto/                     # 入参出参，带校验装饰器
  └─ <module>.module.ts
```

- Controller 不写业务逻辑，Service 不碰 HTTP 细节，Repository 不写业务规则。
- 跨模块调用只能走模块的**对外服务接口**，禁止引用对方内部实现类（CI 静态检查）。

### 1.3 日志与错误

- 日志用 `Logger.for(模块名)`，禁止 `console.log`。
- 禁止记录密码、令牌、身份证、完整手机号等敏感字段（框架自动脱敏，不得绕过）。
- 错误必须带错误码（见 [API 文档错误码](./40-api-spec.md)），新增错误码同步更新该表与 PRD-001。

### 1.4 配置

- 任何魔法值必须进配置或常量；新增配置项同步 `.env.example`、配置文档与 zod schema。
- 禁止在代码中按环境名分支（`if (env === 'prod')`），差异走配置项。

### 1.5 前端（后台模板）

- 组件 `PascalCase` 文件名，页面放 `views/<模块>/`，通用组件放 `components/`。
- 权限控制一律用 `v-permission` 指令或权限码判断，**禁止只靠隐藏按钮**（服务端仍须校验）。
- 列表页统一用 `<CrudTable>`，不得各写一套分页逻辑。
- 请求统一走封装的 request 层，禁止组件内直接 `fetch/axios`。

### 1.6 注释规范（中文 + 日期 + 作者）

**总纲**：注释一律使用**简体中文**（专业术语保留英文原词，如 JWT / Redis / RBAC / upsert，不强行翻译）；每个源文件必须有**文件头注释块**，标明**作者**与**日期**；注释只写「为什么」，不写「做什么」（代码本身已说明的部分不重复）。

#### 1.6.1 文件头注释（强制）

每个源文件首行必须是文件头注释块，格式如下：

```ts
/**
 * @file 用户服务
 * @description 负责用户增删改查与角色分配；事务边界在本层，跨模块调用只允许走本服务接口。
 * @author donttemo
 * @created 2026-10-09
 * @module user
 * @since v0.1.0
 */
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `@file` | 是 | 文件名或一句话职责概括，≤ 30 字 |
| `@description` | 是 | 这个文件「做什么 + 边界在哪」；框架包必须写清对外契约 |
| `@author` | 是 | 作者署名，须与 `git config user.name` / 提交记录一致；**本仓库统一为 `donttemo`**；多人协作写主要作者 |
| `@created` | 是 | 首次创建日期，格式 `YYYY-MM-DD`（本地时区）；**创建后不再改动** |
| `@modified` | 否 | 语义发生变更时逐条追加：`@modified 2026-10-15 donttemo 补充软删过滤（PRD-003）` |
| `@module` | 否 | 所属业务模块或包名 |
| `@since` | 否 | 引入该文件的框架版本号 |
| `@generated` | 否 | 由代码生成器产出，见 §1.6.5 |

规则：

1. `@created` 只在文件创建时写一次，**重构、格式化、批量改样式不得刷新日期**；语义变更追加 `@modified`，保留历史条目。
2. `@author` 取值：本仓库统一 `donttemo`；新成员加入时保持与其 `git config user.name` 完全相同，禁止同一人出现多个署名（如昵称 + 全名混用）。
3. 新建文件由脚手架 / IDE 模板自动生成文件头，作者取 `git config user.name`（当前 `donttemo`），日期取当天；外部贡献者用 `donttemo` 之外的本名并在 PR 中说明。

#### 1.6.2 各类注释的写法

| 场景 | 要求 |
|---|---|
| 导出的类 / 接口 / 类型 | 必须 JSDoc，中文说明用途与约束 |
| 导出的函数 / 方法 | 必须 JSDoc，含 `@param` `@returns`；可能抛业务异常的写 `@throws` + 错误码 |
| 装饰器（如 `@Cacheable`） | 说明生效条件与副作用（如缓存键组成、失效时机） |
| 非直觉代码 / 绕坑逻辑 | 行内注释写「为什么这么写」+ 依据（PRD 编号、issue、方言差异） |
| 常量 / 枚举 | 注释说明取值含义与单位（如「单位：秒」） |
| 配置项 | schema 中用 `.describe('中文说明')`，与注释同源 |

示例：

```ts
/**
 * 计算订单应付金额
 * @param order 订单实体，金额字段为 decimal 字符串，禁止转浮点
 * @param coupon 优惠券，为空表示不使用
 * @returns 应付金额字符串（保留两位小数）
 * @throws 2001 优惠券不可用
 */
```

#### 1.6.3 标记注释（TODO / FIXME）

必须带责任人与日期，且关联任务，禁止裸 `TODO`：

```ts
// TODO(donttemo, 2026-10-09): 支持按部门过滤，待 PRD-003 数据权限落地（T-M3-07）
// FIXME(donttemo, 2026-10-12): PG 下 upsert 并发冲突需改写为 ON CONFLICT，见 PRD-002
```

- `TODO` 超过 30 天未处理，评审时转为独立任务或直接删除。
- CI 检查 `TODO` 格式，无责任人/日期的标记视为缺陷。

#### 1.6.4 其它文件类型

| 类型 | 文件头形式 |
|---|---|
| Vue SFC | `<template>` 之前用 `<!-- @file ... @author ... @created ... -->`；`<script setup>` 内可用块注释 |
| SQL 迁移 | `-- @file V1_0_1__init.sql @description 初始化权限五表 @author donttemo @created 2026-10-09` |
| YAML / Dockerfile / Nginx | `# @file ... @author ... @created ...` |
| Python / Shell 脚本（工具链） | `# -*- coding: utf-8 -*-` 后接 `# @file ...` |
| Markdown 文档 | 文件头不强制，但表格上方须有中文说明；重大修订在文末记「修订记录：日期 / 作者 / 摘要」 |

#### 1.6.5 生成代码（`@generated`）

- 生成器产出的文件头部标注 `@generated by @fw/cli 2026-10-09`，作者字段填执行生成的人。
- 带 `@generated` 的文件**禁止手工修改**；需要扩展请走 `*.base.*` 继承或钩子。确需手改时，先删除 `@generated` 标记并补 `@modified`。

#### 1.6.6 禁止事项

1. 行尾无意义注释（`i++ // 加一`）、复述代码的注释。
2. 大段被注释掉的代码（要恢复请用版本控制，直接删除）。
3. 中英夹杂的半吊子注释、拼音注释、表情符号。
4. 注释里写密钥、真实账号、内部域名之外的敏感信息。
5. 批量刷新他人文件的 `@author` / `@created`。

#### 1.6.7 自动化校验

- 命令：`pnpm run check:headers`（脚本 `scripts/check-file-headers.mjs`），扫描 `packages/`、`apps/`、`templates/`；
- 规则：缺文件头、`@author` 或 `@created` 缺失、日期格式非 `YYYY-MM-DD`、`TODO` 无责任人 → **CI 阻断**；
- `--fix` 仅对缺头文件按模板追加（作者取 `git config user.name`，未配置时回退默认署名 `donttemo`，日期取当天），不修改已有头。

#### 1.6.8 对撞类门禁（并行架构的漂移防线）

「契约先行 + mock 顶上」与「框架包 / 参考应用 / 项目模板三份同源实现」都靠对撞门禁防漂移，均在 CI 的 base 作业阻断合并：

| 门禁 | 命令 | 对撞内容 |
|---|---|---|
| 前后端接口对撞（C-06） | `pnpm run check:api-parity` | `apps/admin-web` 前端调用面 ↔ 全仓 `*.controller.ts` 后端路由面；前端调了后端没有即失败，反方向仅提示 |
| 审计事件 | `pnpm run check:audit-events` | 事件注册表（`@fw/auth` 源码直读，不生成第二份码表）↔ 生产代码：`event:` 与 `recordEvent('…')` 出现未登记码即失败；注册表每个未废弃条目必须在代码中有写入点；`docs/45` §7 覆盖矩阵必须逐条列出；mock 侧注册表为生成物，与后端逐字节不一致即失败（PRD-015 FR-15-21） |
| 三方一致性 | `pnpm run check:triway-consistency` | 框架包 ↔ example-api ↔ admin 模板六轴：① 模板前端调用面 ⊆ 模板路由面（含按装配判定的框架包控制器）；② 模板路由面 ⊆ example-api 路由面（模板是参考实现的裁剪子集）；③ 权限码以框架 `PERM`/`QUEUE_PERM_*` 为权威，两侧种子声明与控制器守卫、模板前端使用逐一闭环；④ 两 Prisma schema 共有模型字段一致（`@fw/auth` Store 契约）；⑤ 模板 `@fw/*` 依赖存在且 `workspace:*`、import 必已声明；⑥ 模板 `.env.example` 配置键 ⊆ `ENV_KEY_PATHS` ∩ example-api `.env.example` |

- 两个对撞门禁共用 `scripts/lib/api-parity-core.mjs`（路径归一化 / 调用面 / 路由面提取）——同一条路径必须在两个门禁里算出同一个键；
- 对撞门禁的护栏本身也要反向验证：注入突变（加一个只有模板有的路由 / 发明一个权限码 / 改一处依赖规格）必须挂红，已随首次交付逐轴验过。

### 1.7 反模式清单（评审直接打回）

1. 业务层出现 `if (driver === 'redis')` 之类的实现分支。
2. Controller 里写 SQL 或直接访问 Repository 之外的存储。
3. 裸 `catch {}` 吞异常，或 catch 后不打日志。
4. 硬编码密钥、URL、环境判断。
5. 前端隐藏按钮但接口无权限校验。
6. 新增接口未标注权限点（CI 会拦）。
7. 测试依赖手工数据或用例间顺序。
8. 修改已提交的迁移文件。
9. 文件缺中文文件头（无 `@author` / `@created`）、注释用英文、或批量刷新他人文件的作者与日期。

## 2. Git 规范

### 2.1 分支模型（主干开发 + 短分支）

| 分支 | 说明 | 保护 |
|---|---|---|
| `main` | 始终可发布 | 禁止直接 push，需 PR + CI 全绿 + 1 人以上评审 |
| `feat/<prd>-<短名>` | 功能分支，如 `feat/prd003-rbac` | 生命周期 ≤ 1 周 |
| `fix/<issue>-<短名>` | 缺陷修复 | — |
| `chore/<短名>` | 工程与文档 | — |
| `release/v<x.y.z>` | 发布准备（可选） | — |

- 分支从 `main` 拉取，合并前 `rebase` 到最新 `main`，保持线性历史。
- 合并策略：功能分支 `squash merge`（一条提交一个语义单元）；`release` 分支用 `merge commit` 保留历史。

### 2.2 提交信息（Conventional Commits）

```
<type>(<scope>): <主题>          # 主题 ≤ 72 字符，祈使句，结尾无句号

<body>                            # 可选：说明为什么，不重复代码内容
<footer>                          # 可选：Refs: PRD-003 / TC-AUTH-004 / Closes #123
```

| type | 用途 |
|---|---|
| `feat` | 新功能 |
| `fix` | 缺陷修复 |
| `refactor` | 重构（无行为变化） |
| `perf` | 性能优化 |
| `test` | 测试相关 |
| `docs` | 文档 |
| `chore` | 构建、依赖、工程配置 |
| `revert` | 回滚 |

scope 用包名或模块名：`core` / `config` / `logger` / `orm` / `cache` / `auth` / `queue` / `cli` / `web` / `docs`。

示例：`feat(auth): refresh token 轮换与重放检测`

### 2.3 其它

- `.gitignore`：忽略 `node_modules`、构建产物、`.env*`（`!.env.example`）、日志与本地数据库文件。
- **禁止**提交密钥、证书、真实数据、大于 1MB 的二进制文件（大文件走对象存储或 Git LFS）。
- 标签：发布时打 `v<x.y.z>` 附注标签，与 CHANGELOG 条目一一对应。

## 3. PR 规范

### 3.1 提交前

- [ ] 分支已 rebase 到最新 `main`；本地 `pnpm lint && pnpm test && pnpm build && pnpm run check:headers` 全绿。
- [ ] PR **越小越好**：目标 ≤ 400 行改动、≤ 1 周生命周期；超过则拆分（「重构 + 功能」必须分开）。
- [ ] 一句话说清「改了什么、为什么、怎么验证」。

### 3.2 PR 描述（模板见 `.github/PULL_REQUEST_TEMPLATE.md`）

必填：关联 PRD 与任务 ID、变更类型、影响面（是否需要迁移/配置变更/文档更新）、验证方式（命令或用例编号）、截图（前端改动）。

### 3.3 评审清单（评审人逐条确认）

- [ ] 符合分层约束与依赖方向，无跨模块内部引用。
- [ ] 无硬编码密钥/环境分支/裸异常/敏感日志。
- [ ] 新增能力有可替换性设计（接口 + 适配器），未把实现细节泄漏给业务层。
- [ ] 新增接口已标注权限点；涉及权限的补了越权用例。
- [ ] 测试覆盖到边界与异常分支；无顺序依赖。
- [ ] 注释为简体中文；新增/修改文件有文件头且 `@author`、`@created` 完整；`TODO` 带责任人与日期。
- [ ] 文档同步：PRD / API / 运维 / CHANGELOG（按需）。
- [ ] 满足 [DoD](./10-acceptance-criteria.md) 全部条目。

### 3.4 合并条件（全部满足）

1. CI 全绿（lint、单测、集成矩阵、覆盖率、依赖扫描、注释头校验、spec 一致性）。
2. 至少 1 名非作者评审通过（框架包变更需 2 名，含架构负责人）。
3. 所有评审意见已解决或明确记录为后续任务。
4. 无 P0 缺陷遗留；P1 缺陷需带责任人与闭环时间。

### 3.5 评审礼仪

- 24 小时内首次响应；区分 `必须改` / `建议` / `疑问` 三类意见。
- 作者回复时说明「已改 / 为何不改」，不静默忽略。
- 评审不通过时给出具体理由与替代做法，避免只说「不好」。

## 4. 版本与发布

- 版本号遵循语义化版本，变更记入 [CHANGELOG](../CHANGELOG.md)。
- 发布流程：预检（备份、迁移可逆性）→ 灰度 → 全量 → 验证，详见 [运维手册](./60-deployment-ops.md) 第 12 节。
- 破坏性变更必须：写 ADR（或更新）、在 CHANGELOG 标注、提供迁移步骤、API 保留至少一个版本周期。
