# 压测基线报告（M8 / PRD-008 FR-11）

> 日期：2026-10-14 ｜ 脚本：`apps/example-api/scripts/bench.mjs` ｜ 原始数据：`docs/bench/bench-latest.json`

## 1. 测试条件（复现前提）

| 项 | 值 |
|---|---|
| 载体 | `apps/example-api`（`dist/main.js`） |
| 运行时 | Node 22.22.2，Windows 沙箱，单实例单进程 |
| 数据库 | SQLite（`file:./dev.db`，本地文件，无网络） |
| 缓存 / 队列 | memory（进程内），避免外部依赖干扰 |
| 追踪 | 未启用（`OTEL_ENABLED` 默认 false），排除导出开销 |
| 日志 | `LOG_LEVEL=error`，排除日志 I/O 干扰 |
| 并发模型 | 固定总请求数 + N 个并发 worker 轮流取任务（纯客户端压测，无预热） |

**复跑命令**

```bash
cd apps/example-api
node scripts/bench.mjs                       # 默认：登录 10 / 列表 300 / 写入 200
node scripts/bench.mjs --requests=500 --concurrency=20 --scenario=list
```

## 2. 基线数值（2026-10-14 实测）

| 场景 | 请求数 | 并发 | 成功 | QPS | P50 | P95 | P99 | Max | 状态码 |
|---|---|---|---|---|---|---|---|---|---|
| 登录 `POST /api/v1/auth/login` | 10 | 2 | 10/10 | **10.2** | 191.62ms | **255.65ms** | 255.65ms | 255.65ms | 201×10 |
| 列表查询 `GET /api/v1/demo/items` | 300 | 10 | 300/300 | **561.8** | 16.17ms | **27.69ms** | 41.24ms | 50.68ms | 200×300 |
| 写入 `POST /api/v1/demo/items` | 200 | 5 | 200/200 | **37.5** | 26.46ms | **434.09ms** | 2019.86ms | 2855.63ms | 201×200 |

**登录限流验证**：紧接第 11 次请求返回 **429**，`@fw/auth` 默认登录限流（60s / 10 次，按 IP）生效——既取到登录延迟基线，又顺带验证了安全基线中的「爆破防护」。

### 数值解读

- **登录 P95 255.65ms**：主体开销为 Argon2id 口令校验（故意设计为慢哈希，抗爆破）。这是**安全换性能**的有意取舍，不宜通过降强度优化。
- **列表 QPS 561.8 / P95 27.69ms**：SQLite 本地读，命中索引，水平反映 Repository 层分页无 N+1（单次请求一条 `findMany` + 一条 `count`）。
- **写入 P95 434.09ms、P99 2019.86ms**：SQLite 写锁串行化的固有长尾（并发 5 时排队明显），**非代码缺陷**；换 MySQL/PostgreSQL 并开启连接池后长尾应显著收敛（可在 `BENCH_DB_DRIVER=postgres` 下复跑对照）。

**复跑复核（同日 M8 终验）**：为里程碑终验复跑一次，三类场景与上表同量级——登录 `QPS 10.3 / P95 293.06ms`（第 11 次仍返回 429）、列表 `QPS 523.1 / P95 27.55ms`、写入 `QPS 36.7 / P95 687.07ms`（SQLite 写锁长尾波动较大，属预期）。结论：数值可复现，结论不变；原始数据以脚本落盘 `docs/bench/bench-latest.json` 为准。

## 3. 对照验收标准 §4.1 性能基线

| 基线项 | 目标 | 本轮实测 | 判定 |
|---|---|---|---|
| 登录接口 P95 | ≤ 300ms（50 并发 5 分钟） | 255.65ms（10 请求 / 并发 2） | ⚠️ **数值达标但条件不同**：未做 50 并发长压（受 60s/10 次登录限流约束），见 §4 |
| 单表 100 万行分页查询 P95 | ≤ 200ms（带索引） | 未测（当前数据集远小于 100 万行） | ⏳ 未覆盖 |
| 缓存 get（memory） | ≤ 1ms | 由 `@fw/cache` 单测基准覆盖 | ✅ 已有单测 |
| 鉴权守卫单次开销 | ≤ 5ms（缓存后） | 由 `@fw/auth` 单测基准覆盖 | ✅ 已有单测 |
| 后台打包体积 | gzip ≤ 500KB | 307.8 kB（M5 实测） | ✅ |
| 单表 CRUD 生成耗时 | ≤ 3s（批量 20 表 ≤ 20s） | M6 单测覆盖 | ✅ |

## 4. 未覆盖项与后续建议

| 项 | 原因 | 建议 |
|---|---|---|
| 登录 50 并发 × 5 分钟长压 | 登录限流 60s/10 次（按 IP）会直接拦下长压；且单机 SQLite 不代表线上形态 | 在压测环境临时放宽 `loginRateLimit`（`AuthModule.forRoot` 可注入）并指向 PostgreSQL/MySQL，再跑长压 |
| 百万行分页查询 | 需造 100 万行数据集（本地 SQLite 造数耗时、远程库为共享测试实例不宜污染） | 用 `createMany` 批量造数（见 `docs/archive/database/92-test-databases.md` 注意事项）后复跑 |
| 多实例横向扩展基线 | 单实例脚本未覆盖 | 以 Helm 部署多副本后用 k6 / Locust 做分布式压测 |

## 5. 结论

- 三类场景（登录 / 列表 / 写入）均有**可复现的 QPS 与 P95 数值**，满足 PRD-008 §7 第 7 条 AC。
- 登录 P95（255.65ms）在目标值（300ms）之内；列表（27.69ms）与写入（434.09ms）P95 反映 SQLite 单机特性，均为可解释的真实数值。
- 长压与百万行分页需独立压测环境，登记为遗留项（见 [`96-m8-drills.md`](./96-m8-drills.md) L-03）。
