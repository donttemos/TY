# 增强功能规划（v0.5.x–v0.6.x 输入稿）

> **本规划已收编为 [PRD-010 · 下一阶段增强：多实例一致性收口与模板生态](./prd/prd-010-next-stage-enhancements.md)（M10，草案）**——需求变更自 PRD-010 起在该文件「变更记录」中追加，本文档保留为评估依据与 E-01~E-17 的原始论证。

> 依据：v0.4.0 发布验收报告（[90-release-v0.4.0.md](./90-release-v0.4.0.md)）、[80-project-plan.md](./80-project-plan.md) 当前快照、
> [40-api-spec.md](./40-api-spec.md) Backlog 标注、[95-doc-audit.md](./95-doc-audit.md) 遗留矩阵、[98-scale-checklist.md](./98-scale-checklist.md) 自检口径。
> 编号规则：新增遗留用 `E-*`（Enhancement），不与 `L-*`（长期）/ `R3-*`（v0.3.0）/ `R4-*`（v0.4.0）冲突。

## 1. 现状盘点（能力边界）

M1–M9 已全部交付：核心骨架、多库抽象、RBAC 鉴权 + 数据权限四档、缓存三防护、管理后台、CRUD 生成器、队列与调度、多租户/传输/追踪/部署模板、配置中心热更（含一键回滚 + Nacos 驱动示例）。租户管理（N-01）、异步导出任务中心（N-02）、列表排序收口、Redis Cluster 实测（L-04）均已闭环。

**核心判断：单实例叙事已闭环，下一阶段的主线是「多实例与规模化叙事」+「模板生态补全」。** 当前三处进程内存态（任务中心、配置快照历史、登录限流计数）在多副本部署下会打破「业务代码零改动规模演进」（G2）的承诺。

## 2. 潜在不足与边界情况（评估结论）

| # | 类别 | 问题 | 触发条件 / 边界 | 影响 |
|---|---|---|---|---|
| A-1 | 无状态性 | `JobCenterService` 是**进程内存登记表**（进度/产物/重跑均在本进程） | 多副本部署：派发请求落在实例 1、进度/下载/重打请求落在实例 2 → 404 | 违反 98 清单 7.1「应用无状态」自检点；Helm 多副本 + Nginx 轮询下必然复现 |
| A-2 | 无状态性 | `@fw/config-center` 快照历史是**进程内环形表（20 版）**，回滚历史只存在于处理请求的实例 | 多副本：A 实例写入 v21，B 实例回滚找不到该版本；file 驱动多实例依赖共享文件系统（K8s PVC） | 配置漂移、回滚语义不一致；nacos 驱动已写但未入 `CONFIG_CENTER_DRIVER` 枚举 |
| A-3 | 默认安全 | G5 承诺「限流默认开启」，实际只有**登录安全限流**（`login-security.ts`）+ Nginx 层登录限流；业务 API 无框架级限流中间件 | 忘记配 Nginx 的部署形态（裸 Node / Helm 直暴露）→ 业务接口裸奔 | 与设计原则承诺不符；暴力枚举、CC 打消耗无框架级兜底 |
| A-4 | 契约悬空 | `GET /permissions/tree` 在 api-spec §1 有契约、标注 Backlog，前端未消费，parity 检查仅提示 | 已是当前**唯一**的悬空契约 | 菜单/权限选择器只能拉平表自行拼树，每个落地项目重复劳动 |
| A-5 | 扩展点 | `AUTH_STRATEGY` 枚举含 `session/oauth2/apikey`，但仅 `jwt` 有端到端路由（M3 遗留 ①，两次登记未排期） | 企业内网 SSO / 开放 API 签名场景即空白 | 模板宣称「多策略可切换」但实际只有一条路径 |
| A-6 | 扩展点 | `@fw/queue`（bullmq）与 `@fw/transport` 的 redis-cluster 支持未评估（L-04 收口时明确划出的范围边界，hash-tag 语义） | 大档部署（Redis Cluster）+ 队列持久化组合 | 「大档承诺」里的 Kafka/Cluster 组合无实测依据 |
| A-7 | 边界情况 | 审计日志无归档/分区策略：只有导出与查询，单表无限增长 | 审计量大的系统运行数月后列表与统计退化 | 98 清单 1.4 的 P95 口径只在 100 万行内承诺 |
| A-8 | 模板生态 | `templates/` 只有 `api` + `codegen`；`fw new --template=admin|cms` 无对应模板资产（README 目标体验宣传 admin 模板） | 新项目脚手架第一步即缺 | G1「1 天骨架」承诺只有 api 形态可兑现 |
| A-9 | 实时性 | 任务进度、死信告警、队列统计全靠前端轮询（退避 1s→10s） | 任务完成感知最慢 10s；告警无主动触达 | 体验增强向；也是消息通知中心（站内信）的地基 |
| A-10 | 边界情况 | 前端 keep-alive LRU 上限 12、死信分页上限 200、产物上限 20MB、配置历史 20 版——均有意为之，但**均未在文档中集中说明上限可配性** | 落地项目踩到上限时只能改源码 | 文档与配置化收口即可，工作量小 |

## 3. 完善项清单（按优先级）

### P0 — 多实例一致性收口（v0.5.0 主线，兑现 G2）

| 编号 | 完善项 | 目标 | 预期收益 | 验收口径 | 依赖 |
|---|---|---|---|---|---|
| E-01 | **任务中心驱动化**：抽 `JobCenterPort`，memory（现行为，默认）+ bullmq/db 双驱动，产物存对象存储或落库 | 多副本下进度/下载/重跑任意实例可达 | 打破 Helm 多副本最后一处进程态；98 清单 7.1 可勾选 | 单测含双驱动；`smoke-admin` N-02 段在 2 副本形态复跑通过 | 无 |
| E-02 | **配置中心多实例语义**：快照历史下沉持久层（或经 transport 广播版本推进）；`nacos` 驱动转正入枚举并出装配示例文档 | 回滚/版本号全局一致；集群形态有明确推荐路径 | M9 收官；「规模化叙事」在配置面闭环 | 环形表语义保留为 memory 驱动行为；nacos 转正含单测（已有 9 条桩测试可复用） | 可与 E-01 并行 |
| E-03 | **框架级 API 限流中间件**：令牌桶（复用 `@fw/cache` 驱动实现分布式限流），按路由组/全局两级配置，默认对全部业务路由开启、可白名单豁免 | G5「限流默认开启」从登录面扩展到业务面 | 框架兜底取代部署层自觉；降级策略与 cache 三防护同构（fail-open 可配） | 单测 + smoke 阶段（超限 429 + 白名单豁免 + 分布式语义注释）；60 手册 §3 增键 | cache 分布式锁已有 |
| E-04 | **`/permissions/tree` 契约落地**：菜单/按钮/接口三层树端点 + 前端消费（菜单选择器、权限码选择器换数据源） | 消除当前唯一悬空契约 | 落地项目免自拼树；前端两处选择器简化 | api-spec 该行去除 Backlog 标注；`check-api-parity` 零提示 | 无 |

## 4. 排期建议（映射到版本）

| 版本 | 建议范围 | 主线 |
|---|---|---|
| v0.5.0 | E-01 ~ E-04 | **多实例一致性收口**（无状态化 + 限流默认开启 + 权限树） |
| v0.5.x 小版本 | E-05 ~ E-07 | 规模化遗留（K8s / cluster / 多策略），环境依赖决定先后 |
| v0.6.0 | E-08 ~ E-11 | 模板生态（admin 模板 + storage + 审计归档 + 压测） |
| 穿插/按需 | E-12 ~ E-17 | 体验项，SSE/站内信可视需求提前 |

原则：P0 四项不引入新外部依赖（除 E-01 的持久化可选实现），全部有既有单测/冒烟纪律可复用；E-05/E-06 是**环境依赖**项，建议与任意版本并行、到位即做，避免长期不闭环（95 报告风险 ② 同款结论）。

## 5. 明确不做（与非目标对齐）

营销页/大屏（NG5）、低代码运行时（NG4）、自研基础设施（NG2）、Kafka 驱动（O-5 评估结论：bullmq 已覆盖承诺场景，引入即新增维护面——如需可按端口新增适配，不排期）、公有云托管运营（NG7）。
