# ADR-0013 · 异步任务中心用进程内存登记表，任务面只验归属人

- 状态：已采纳
- 日期：2026-10-15
- 关联：PRD-003、PRD-007、[api-spec §3.11](../40-api-spec.md)、[docs/99](./../99-admin-web-enhancement-and-fixes.md)（N-02）

## 背景

1. 审计导出（N-02）与租户隔离级别迁移（N-01）都是「点击后要跑几秒到几十秒」的操作：同步返回会让请求超时，前端也没有进度反馈，违背原型 §7「导出/批量走异步任务」。
2. api-spec §3.8 曾定稿「异步业务进度沿用业务表存 jobId + 自查进度，M7 不实现通用 `/jobs/:id/progress`」——即每个业务各建一套进度机制。N-01/N-02 同期落地时出现两个消费方，重复造两套的代价已经大于抽象一套。
3. 任务进度是**短生命周期**数据（跑完即下载，下载完即弃）：为它新增一张 job 表意味着 schema 变更要过三库矩阵（sqlite/mysql/postgres）+ 数据字典 + 生成器映射，而收益只是「重启后还能查旧任务」。
4. 任务面的权限语义没有先例：若按业务资源发权限码（`job:read` 等），每个派发方都要额外授权，且任务详情里的 `params`/`error` 可能带业务敏感信息，权限面越宽泄露面越大。

## 决策

框架提供**进程内存任务登记表** `JobCenterService`（`apps/example-api/src/modules/jobs/`）：

1. **存储**：进程内存 Map，按 `ownerId` 隔离；**不建表、不落库**。重启即失效，对已失效 id 与从不存在的 id 一律 `404`（语义一致，不区分「过期」与「不存在」）。登记表设容量上限并裁剪最旧终态任务，防内存泄漏。
2. **端点面**：`GET /jobs/:id/progress`、`POST /jobs/:id/retry`、`GET /jobs/:id/download`——**只验登录 + 归属人**，不设业务权限码。不存在的任务 / 非归属人一律 `404`，不泄露存在性。
3. **派发侧把关**：业务权限码在派发入口校验（`/audit-logs/export` 需 `audit:export`，`/tenants/:id/migrate` 需 `tenant:manage`）。任务面本身是「我自己的任务」，不重复授权。
4. **契约**：统一 `JobView` 快照（`status/progress/message/timeline/error/traceId/artifact`），进度 `report()` 单调收敛，产物上限 20MB（超出即失败终态），仅 `failed` 可原地重跑。
5. **传输**：`download` 走 `@Res()` 裸文本流（统一信封拦截器对 `headersSent` 不二次包装），`Content-Disposition` 用 RFC 5987 `filename*`。

## 备选方案

| 方案 | 优点 | 缺点 | 未选原因 |
|---|---|---|---|
| **进程内存登记表（本决策）** | 零 schema 成本、零迁移；重启失效语义可自洽（统一 404）；单测可同步驱动 | 多实例部署各自为政；重启丢进行中任务 | — |
| 新建 `jobs` 表（DB 持久化） | 重启后可查、跨实例共享 | schema 变更要过三库矩阵 + 数据字典 + 生成器映射；为短生命周期数据付长期成本；需额外清理策略 | 成本远超收益 |
| 复用 `@fw/queue`（BullMQ）持久化任务 | 已有队列与死信能力 | 队列语义是「投递一次」，进度查询/产物下载/原地重跑都要另建面；引入 Redis 依赖违背小系统零依赖起步 | 杀鸡用牛刀，且耦合部署形态 |
| 每业务各建进度机制（api-spec §3.8 原方案） | 无跨模块契约 | 两个消费方就要写两套，第三个必然继续复制；前端任务条无法通用 | 已实际撞墙 |

## 后果

**正面**：
- 前端 `useJobCenter` + `JobBar.vue` 一处实现，所有异步操作（审计导出、租户迁移、后续批量任务）直接复用。
- 无 schema 变更，三库矩阵、数据字典、生成器映射均不受影响。
- 归属人隔离把「任务详情泄露」面压到最小：他人任务与不存在任务同返 404。
- 派发侧权限码不变，授权模型不出现新的权限点。

**负面 / 代价**：
- **多实例水平扩展时任务不共享**：用户请求落到 A 实例，轮询落到 B 实例会 404。当前部署形态为单实例（systemd / 单容器），可接受；上多实例前必须改造成共享存储或粘性会话。
- 重启丢进行中任务：长迁移（租户隔离级别切换）若恰逢重启，前端会看到任务 404，需重新触发。控制面切换本身幂等（写 isolation + 连接串），重试安全。
- 进程重启后 sessionStorage 里的旧 jobId 全部失效：`useJobCenter.restore()` 按 404 清理并重建登记表，用户侧表现为任务条清空。

**缓解措施**：
- ADR 与 api-spec §3.11 明示「进程内存、重启失效」，部署文档（docs/60/61/62）在讲横向扩展时引用本条。
- 前端轮询对 404 做终态处理（标记 stale 后移除），不无限重试。
- 若未来需要跨实例，优先在 `JobCenterService` 背后换共享存储实现（端口已隔离：登记/查询/产物三组方法），端点契约不变。
