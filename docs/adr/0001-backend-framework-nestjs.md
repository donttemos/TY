# ADR-0001 · 后端框架采用 NestJS

- 状态：已采纳
- 日期：2026-10-09
- 关联：PRD-001、[愿景与范围](../00-vision-scope.md)

## 背景

1. 本项目要做的不是业务系统，而是「框架之上的框架」，需要**强模块化与依赖注入**来支撑能力替换。
2. 同一套代码要覆盖小（单机）到大（微服务）三种形态，框架必须同时支持单体与分布式形态。
3. 团队需要 TypeScript 全栈，前后端同语言以降低协作成本。
4. 生态与招聘成本是长期约束，不能选小众框架。

## 决策

后端框架采用 **NestJS**（TypeScript），以 Module / Provider 组织框架包，所有可替换能力通过 DI token 注入实现。

## 备选方案

| 方案 | 优点 | 缺点 | 未选原因 |
|---|---|---|---|
| Express / Fastify 裸写 | 极轻、可控 | 无模块化与 DI，框架能力要靠自建约定 | 规模一大即失控，与「做框架」目标相悖 |
| NestJS | 模块化、DI、装饰器、内置微服务 transport、生态成熟 | 抽象较多，启动略慢，学习曲线中等 | — |
| Spring Boot（Java） | 企业生态最强 | 与 TS 全栈目标冲突，小系统偏重 | 作为备选栈，不在首版范围 |
| Kratos / go-zero（Go） | 性能好、微服务友好 | CRUD 类后台开发效率低于 TS | 同上 |

## 后果

**正面**：模块化天然契合「能力可插拔」；`Transport` 抽象让单体→微服务只改配置；生态成熟（Passport、TypeORM/Prisma、BullMQ 均有官方或成熟集成）。

**负面 / 代价**：启动时间高于裸 Express（基线要求 ≤ 1.5s，需在 M1 验证）；装饰器与 DI 有一定学习成本；框架升级属破坏性变更风险点。

**缓解措施**：框架包与业务模块严格分层，业务代码不直接依赖 NestJS 的 transport 细节；锁定 NestJS 大版本并在 CHANGELOG 标注升级影响；M1 建立冷启动基线用例（TC-NFR-001）。
