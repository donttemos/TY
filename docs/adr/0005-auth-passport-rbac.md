# ADR-0005 · 鉴权用 Passport 策略 + 自研 RBAC，不引入 Casbin

- 状态：已采纳
- 日期：2026-10-09
- 关联：PRD-003

## 背景

1. 认证方式需可插拔：JWT（默认）、Session（内网）、OAuth2（微信/企微/GitHub）、API Key（开放接口）。
2. 授权模型首版为 RBAC（用户-角色-权限），M8 才扩展到数据权限与组织维度。
3. 需避免为「未来可能的 ABAC 需求」提前背上复杂引擎的维护成本。

## 决策

- **认证**：使用 Passport 的策略机制，每种认证方式一个策略，由 `AUTH_STRATEGY` 与路由元数据选择。
- **授权**：自研 RBAC —— 五张表（users/roles/permissions/user_role/role_permission）+ 权限点编码 `资源:操作` + `@Permissions()` 装饰器与全局守卫。
- **不引入 Casbin**；但守卫设计保留扩展点，若将来出现 ABAC / 复杂策略需求，以新增 ADR 的方式引入。

## 备选方案

| 方案 | 优点 | 缺点 | 未选原因 |
|---|---|---|---|
| Casbin | 支持 RBAC/ABAC/多模型，策略表达力强 | 模型配置复杂、调试成本高、与业务表需同步 | 首版 RBAC 需求用不上，属过度设计 |
| 完全自研认证 | 无依赖 | 重复实现 OAuth2 等标准流程，易出错 | 标准流程应复用成熟实现 |
| Passport + 自研 RBAC | 认证标准复用、授权模型简单可控 | ABAC 需后续扩展 | — |
| 外包给身份云服务（Keycloak 等） | 功能最全 | 增加运维组件，违背「零依赖起步」 | 与 C1 冲突 |

## 后果

**正面**：认证策略可插拔且实现成本低；RBAC 模型直观、便于后台可视化配置；无额外中间件运维负担。

**负面 / 代价**：ABAC、复杂层级策略需自研扩展；权限模型变更时要迁移既有角色数据。

**缓解措施**：权限点编码统一 `资源:操作` 便于后续映射；`dataScope` 字段与拦截器钩子在 M3 预留，M8 扩展；若出现「角色爆炸」（角色数 > 50 且规则交叉）的信号，触发新 ADR 评估 Casbin。
