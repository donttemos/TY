# ADR-0032 · 业务可读审计的事件模型与解释机制

- 状态：**提案**（2026-10-20，随 PRD-015 一并评审）
- 关联：PRD-015（FR-15-01~23）；前置决策 ADR-0025（统一错误与审计事件契约）、ADR-0026（requestId/traceId 分层）、ADR-0013（任务中心与导出）、ADR-0029/0031（套餐订阅与租户五态，事件事实来源）
- 事实基线：2026-10-20 `main@7e1be4a` 源码核实（证据见 PRD-015 §1.2）

## 1. 背景与问题

M12 已把审计的**存储契约**打通（六字段 + 脱敏 + 检索键 + 归档 + 导出），但审计仍是「接口调用记录」，不是「业务事件」：

1. **无语义权威**：`event` 是散落字面量（`'saas.plan.create'`、模板拼接 `saas.lifecycle.${action}`、`'refresh.replay_detected'`），全仓没有事件目录；码可任意拼写，前端无从翻译，也无法回答「系统一共记录了哪些事件」。
2. **无业务快照**：`audit_logs` 只有 `module/action/target_type/target_id/before/after`，没有摘要、对象名称、操作人名称、原因；用户改名、套餐改版后历史记录失去当时的业务含义。
3. **覆盖不对称**：拦截器只在成功回调落库；权限拒绝只写日志；登录失败只计指标。于是「改成功」与「改被拒」在审计里无法区分。
4. **租户维度空转**：`tenant_id` 列存在但写入路径不填（恒 0），查询也不支持该过滤——运营无法按租户拉一条完整链路。
5. **展示层无分层**：详情抽屉把技术字段与业务信息混在一起，运营必须先理解 `module/action/traceId` 才能判断发生了什么。

如果直接用「前端加翻译表 + 多显示几个字段」解决，会得到第三份语义副本（后端码、前端表、字典表各一份），并在下次改名/加事件时再次漂移。需要一次**模型层面**的定案。

## 2. 决策

**审计采用「事件注册表（语义）+ 不可变业务快照（事实）」双轨模型：注册表在代码内单源声明并经只读端点下发；会随时间漂移的业务事实写入审计行并冻结；纯展示字典不落库；结果区分四态并标注记录来源。**

## 3. 决策规则

### R1 事件注册表是唯一语义权威，代码内单源声明

- 位置：`@fw/auth`（`AuditService` 与 `AuditLogRecord` 所在包），新增 `AUDIT_EVENTS` 常量与 `AuditEventDefinition` 类型；**不新建 `@fw/audit` 包**。
- 码形：`<domain>.<verb>`（`auth.login` / `user.create` / `config.change`）或 `<domain>.<aggregate>.<verb>`
  （`saas.plan.publish` / `saas.lifecycle.freeze`），**至少两段**。
  修订记录（2026-10-20，B2 实施）：原定「新事件一律三段」，落地时发现为凑段数会写出
  `auth.session.login` 这类无信息量的码——两段在实体操作上更自然，故放宽为两段起；
  `refresh.replay_detected`（两段，已写入 v0.6+ 历史行）无需改名，命名规则不再需要「历史例外」。
- 下发：新增只读端点 `GET /api/v1/audit-logs/events`（`audit:read`），返回定义数组 + `version`（注册表内容哈希）供前端缓存失效；前端**不维护本地翻译表**。
- 未登记码：测试/开发 fail-fast；生产原样落库 + `logger.error` + 告警，绝不因审计阻塞业务。

**理由**：注册表同时服务三处消费方——写入时校验与补全、导出/归档时渲染中文列、前端展示——单源才能保证三处一致。放 `@fw/auth` 是因为审计写入通道已在该包（`AuditService`），新增包会带来一个只有常量的空壳与额外依赖边。

**被否**：前端本地常量（两份漂移）；数据库事件表（见备选 B）。

### R2 事实快照与解释元数据分层

| 类别 | 字段 | 处置 |
|---|---|---|
| 事实（会漂移） | `summary`、`target_label`、`actor_label`、`reason`、`result`、`audit_source`、`before/after` | 落库，行内冻结 |
| 解释（纯展示） | 事件名称、说明、风险等级、处理指引、字段中文名、枚举值文案、分类 | 注册表，随版本演进 |

**理由**：租户改名、用户改名、套餐编码调整都是常态；若读取时 join 当前业务表，历史记录会被「现在」改写，取证价值归零。反过来，把展示字典也冻结进每一行，则文案纠错/多语言/术语统一都无法回溯修正，且行体积膨胀。

**边界判据**：这个值会不会因为业务数据变更而改变？会 → 快照；不会（只是叫法）→ 注册表。

### R3 摘要写入时固化，三级生成链

优先级：① 调用点显式 `summary` → ② 注册表 `summaryTemplate` 渲染（变量仅取 `target_label` 与 `after` 的安全子集）→ ③ 回退 `"{事件名称}：{对象名称或 ID}"`。

**理由**：摘要必须与导出、归档、离线取证同口径；读取时渲染会把「当时的语义」变成「现在的语义」，且导出端与页面端容易各自实现一套。

**约束**：摘要只陈述事实（谁把什么从 A 改成 B），不写影响、因果与推测——摘要不可变，过度解读无法撤回。

### R4 变更明细不新增列，展示层按注册表映射

`before/after` 已是脱敏快照，作为唯一 diff 数据源；字段中文名与枚举翻译由注册表 `changeFields` 提供（纯数据，不含可执行逻辑）；未登记字段原样显示字段名与值。

**理由**：新增 `changes` JSON 列会与 `before/after` 形成第二事实源，二者不一致时无从判定谁对；把「中文名」当数据存进历史行，等于把展示层版本钉死在业务数据里。

### R5 结果四态 + `audit_source`，HTTP 成功不等于业务成功

- `result`：`success`（业务已完成）/ `denied`（被拒，无业务效果）/ `failed`（已尝试但失败）/ `unknown`（已发起、结果未确认）。
- `audit_source`：`domain`（领域层显式记录）或 `interceptor`（`@Audit` 兜底，仅代表请求成功返回）。
- **硬规则**：PRD-015 高风险清单内的端点必须存在 `domain` 行，且关闭其拦截器元数据（禁止双写）；`interceptor` 行不得作为业务完成的证据。

**理由**：现状拦截器只在 `tap` 落库（PRD-015 U-15-5），一个「接口 200 但异步任务失败」的操作会被记成成功。引入来源标记后，不删除拦截器（大量清单外端点仍受益），但把它的语义降级并显式化。

**`unknown` 的必要性**：进程中断、任务超时、外部依赖结果不明时，记 `failed` 是错误归因，记 `success` 是造假。第四态让「不确定」可以被如实记录。

### R6 拒绝/失败采集有边界，不做「全量失败审计」

- 只对高风险清单内操作采集 `denied` / `failed`：权限拒绝（`authz.denied`，含所需权限码）、租户状态拒绝、非法生命周期迁移、配额超限、认证失败。
- 参数校验 400、资源 404、限流 429 **不落审计**（日志 + 指标已覆盖）。
- `authz.denied` 按「操作人 + 权限码 + 分钟」去重限流（默认单窗口 ≤3 条，超出计数合并）。
- **限流丢弃本身必须可观测**（2026-10-21 补）：`allow()` 返回 false 后调用方直接 return，丢弃若静默，
  「审计样本是否正在大量丢失」无从判断——防洪成功与「审计已经聋了」在运维面上长得一样。
  限流器经 `onDrop` 回调把每次丢弃（`rate_limited` / `capacity` 两种原因）送入
  `fw_auth_audit_dropped_total{path,reason}` 指标 + 每路径每 60s 最多一条的周期性汇总结构化日志；
  汇总刻意不含维度键原文（防把丢弃变成攻击者可控的日志放大面），细节以保留的前 N 条样本为准。

**理由**：审计表是取证资产，不是访问日志。把每次 400 都写进去，会让真正的安全事件淹没在噪声里，并给暴力破解提供刷表放大面（写入成本 × 攻击次数）。「宁可少而准」符合取证语义。
**丢弃可观测的理由**：限流是「有损采集」，有损必须可度量——否则容量调优、副本扩容、攻击处置都失去输入信号；而逐条记录丢弃会把有损放大成新的攻击面（日志/指标双放大），故只做低基数计数 + 周期汇总。

### R7 `tenant_id` 写入 + 与 `dataScope` 交集，存量 0 = 未知

- 写入取请求上下文 `tenantId`（修复当前恒 0）。
- 查询 `tenant_id` 与 `dataScope` 取交集；`self` 档忽略该筛选（防越权放大）。
- 存量 0 读作「未知/存量」，页面标注，不回填、不猜测归属。

**理由**：回填只能靠 `target_id` 反推，猜错比空着更危险——错误归属会让取证指向无辜租户。语义显式化（未知）比「看起来完整」更诚实。

### R8 兼容策略：软增列 + 两表同构 + 三库 + 不回填 + 导出追加

- 新增列全可空（沿 M12 `20261017110000` 先例），在线表与归档表**同一迁移**同构增列。
- 三库（SQLite / PostgreSQL / MySQL）迁移同构，只用可空字符串列，不引入方言特性。
- 历史行不回填；读取按降级链呈现「历史记录（无业务摘要）」。
- CSV **追加**业务列在末尾，既有列序与位置不变。

**理由**：可空列 = 旧代码/旧数据零回归；两表同构是 E-10 不变量（归档不是另一套模型）；追加列序保护下游脚本与 mock 逐字节断言（M12 曾因列序/范围固定断言漏同步导致 CI 红）。

### R9 风险等级与 domain 派生，不落库

- `risk` 与 `domain` 由注册表定义/事件码前缀派生，不新增数据库列。
- 「按风险筛选」由前端取注册表中该风险的 `event` 集合，转成 `event in (...)`（上限 20）下发；`category` 继续只承载 M12 七值粗筛。

**理由**：风险等级是**治理判断**，会随评审调整；落库等于把历史行钉在旧判断上，还要为调整写数据迁移。事件集合规模有限（预期 <100，含 deprecated），多值过滤成本可控；若未来事件数膨胀到集合不可控，再评估落列（登记为演进条件）。

## 4. 备选方案对比

| 方案 | 做法 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| **A 前端翻译表** | 前端维护 `event → 中文` 映射，后端只加列 | 改动最小、无迁移 | 三份语义副本（后端码/前端表/字典），加事件必改前端；导出与归档仍不可读 | 否决 |
| **B 事件元数据入库** | 新建 `audit_events` 表 + `audit_logs.event_id` 外键，元数据可后台维护 | 运营可自助维护文案；支持热更新 | 审计行依赖可变字典，历史解释随字典漂移；多一次 join；三库迁移 + 权限面 + 缓存一致性成本；与「快照不可变」冲突 | 否决（演进条件见 §7） |
| **C 共享常量包** | 抽 `@fw/audit-events` 纯常量包，前后端共同 import | 编译期同源、零网络请求 | 前端为拿常量引入 workspace 包，构建链与版本耦合；元数据变更需前端重新发布；包治理多一条依赖边 | 否决（默认端点下发；若未来需要离线强一致再评估） |
| **D 全部改为领域显式记录，删除拦截器** | 移除 `@Audit` 与 `AuditInterceptor`，所有端点手写审计 | 语义最准、无双写 | 清单外数百端点一次性漏记；回归面过大；与「渐进扩展」原则冲突 | 否决（采用 R5 降级 + 清单内强制） |
| **E 读取时 join 业务表取名称** | 不存 `target_label`，查询时 join `tenants/plans/users` | 零冗余、永远最新 | 历史被改写；跨库（dedicated 租户）无法 join；归档表需回连在线库 | 否决 |
| **F 本 ADR 方案** | 注册表单源 + 事实快照落库 + 解释元数据派生 + 四态来源标记 + 软增列 | 历史准确、口径统一、改动渐进、可门禁 | 行体积增加、需一次性迁移与写入点治理 | **采纳** |

## 5. 最终选择与理由

采纳 **F**（即 R1~R9），理由按优先级：

1. **取证正确性优先于存储经济性**：审计的第一属性是「当时发生了什么」，快照是唯一能保证这一点的实现；冗余几个字符串列远比事后无法证明便宜。
2. **单一语义源优先于分发便利**：注册表单源 + 端点下发，使「加事件」只需改后端一处，且导出/归档/页面天然同口径。
3. **渐进优于重写**：保留 `AuditService`、拦截器、归档、导出、`dataScope` 全部既有能力，只做「加列 + 加注册表 + 收紧写入点」，与 PRD-015 §2.2 的批次顺序一致。
4. **诚实优于完整**：`unknown` 态、存量 `tenant_id=0` 的「未知」标注、旧行「无业务摘要」提示，都是宁可显式承认缺失，也不伪造历史。

## 6. 数据与接口影响

### 6.1 模型增量（`audit_logs` / `audit_log_archives` 同构）

| 列 | 类型 | 可空 | 语义 |
|---|---|---|---|
| `summary` | varchar(255) | 是 | 业务摘要快照（写入时固化） |
| `target_label` | varchar(128) | 是 | 目标对象名称快照（租户名/套餐名/用户名） |
| `actor_label` | varchar(64) | 是 | 操作人名称快照（改名后历史不变） |
| `reason` | varchar(255) | 是 | 操作原因（人工填写或系统生成） |
| `audit_source` | varchar(16) | 是 | `domain` / `interceptor` |

`result` 取值集合扩展 `unknown`（列类型不变，无需迁移）。`tenant_id` 复用既有列（`idx_audit_tenant`）。

### 6.2 注册表条目示意

```ts
export interface AuditEventDefinition {
  code: string;                    // 'tenant.lifecycle.freeze'（稳定，不可改名）
  name: string;                    // '冻结租户'
  description: string;             // 说明发生了什么、有什么影响
  category: AuditCategory;         // 沿用 M12 七值：auth|security|admin|data|config|tenant|system
  risk: 'low' | 'notice' | 'high' | 'critical';
  reviewRequired?: boolean;
  guidance?: string;               // 处理指引（是否需人工复核、下一步）
  targetType?: string;
  summaryTemplate?: string;        // '将租户「{targetLabel}」由 {from} 变更为 {to}'
  changeFields?: Record<string, { label: string; valueLabels?: Record<string, string> }>;
  deprecated?: { since: string; replacedBy?: string };
}
```

### 6.3 端点与契约

| 端点 | 变更 |
|---|---|
| `GET /api/v1/audit-logs/events` | **新增**（`audit:read`）：注册表定义 + `version`；只读、可 ETag 缓存。挂在审计列表域下（同权限、同资源族），**路由必须声明在 `:id` 之前** |
| `GET /api/v1/audit-logs` | 新增过滤 `tenant_id` / `result` / `event`（多值）；响应 additive 增 5 字段 |
| `GET /api/v1/audit-logs/:id` | 响应 additive 增 5 字段 |
| `GET /api/v1/audit-archives` | 与在线同形（含新过滤与新字段） |
| `GET /api/v1/audit-logs/export`、`/audit-archives/export` | CSV 末尾追加 8 列（§6.4） |

无新增错误码；未知过滤参数仍 400/1001（白名单扩项）。

### 6.4 CSV 列序

既有 15 列不变，追加：`eventName,summary,targetLabel,actorLabel,reason,result,auditSource,risk`。

## 7. 影响与风险

**正面**

- 运营视图不再依赖技术字段翻译；详情第一屏即可回答「谁 / 对什么 / 做了什么 / 为什么 / 结果」。
- 历史记录抗业务改名：对象与操作人名称、摘要、原因均为快照。
- 事件可枚举、可门禁：新增事件有固定三件套（注册表 + 写入点 + 矩阵），拼写错误在 CI 拦截。
- 成功/拒绝/失败/未知与「记录来源」显式化，取证结论不再建立在「接口 200」上。
- 在线、归档、导出三处同源解释，减少「页面能看懂、导出的表看不懂」类争议。

**负面 / 代价**

| 代价 | 说明 | 缓解 |
|---|---|---|
| 迁移与双表同步 | 5 列 × 2 表 × 3 库；归档不变量靠人工纪律 | 单一迁移脚本同批改两表；FR-15-23 集成断言；数据字典同步 |
| 写入点一次性治理 | 清单内端点需从拦截器切到领域记录，涉及多处控制器 | 按域分批（认证→生命周期→套餐订阅→配置），每批带覆盖矩阵与回归 |
| 行体积与索引成本 | 摘要/原因等文本列 | 长度上限 + 截断策略；不为文本列建索引；仅 `tenant_id`（已有）参与索引 |
| 摘要不可修订 | 写错即永久 | 摘要只写事实（R3 约束）；评审抽检；错误以新事件追加说明 |
| 注册表成为发布瓶颈 | 加事件必须改后端 | 端点下发 + `version` 缓存；事件定义集中在一个文件，评审成本低 |
| 拒绝审计的写入放大 | 攻击可触发大量 `denied` | R6 去重限流 + 仅清单内事件；监控审计行增速 |
| 前端多一次注册表请求 | 首屏多一个依赖 | ETag/`version` 缓存 + 页面级 store；失败时降级到原始码渲染 |

**演进条件（何时推翻本 ADR）**

- 事件规模超过约 100 条或需要运营自助维护文案 → 重评备选 B（元数据入库 + 版本化），但**行内快照仍保留**。
- 出现合规要求「审计不可篡改」→ 单独立 ADR（哈希链 / WORM 存储），本 ADR 的字段模型可直接承载。
- 需要跨产品复用审计域 → 评估把注册表与 `AuditService` 拆为 `@fw/audit`（届时是搬迁，不是重设计）。
