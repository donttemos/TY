# ADR-0015 · 暗色模式：令牌层双列 + 派生档静态预计算 + 主题三态默认跟随系统

- 状态：已采纳
- 日期：2026-10-16
- 关联：[PRD-010 E-15](../prd/prd-010-next-stage-enhancements.md)、[原型 §2.1](../25-ui-prototype.md)、[ADR-0006](./0006-frontend-vue3-element-plus.md)

## 背景

1. **O-4「前端是否需要暗色模式首发」自原型阶段悬置**（[docs/25 §11](../25-ui-prototype.md)、[docs/95 §5](../95-doc-audit.md)）。M5 已交付「浅色 / 暗色 / 紧凑」三态开关与 CSS 变量骨架，但暗色只有半套：成功 / 警告 / 危险 / 信息四个语义色与文本、背景令牌未按原型 §2.1「暗色列」取值，且 Element Plus 结构令牌与自有 `--fw-*` 令牌形成两套调色板（改一处另一处不跟随）。
2. **主色派生档存在真实缺陷**：`applyPrimaryColor` 对两套主题一律向白混色生成 `light-3..9`，暗色下浅色系被冲淡（按钮 hover 背景发白、tag 浅底刺眼）。
3. **主题只有显式二态**（浅 / 暗），不跟随操作系统偏好；新用户首访在暗色系统下看到亮色界面。
4. 约束：前端产物有 gzip 体积门禁（≤600 kB），主题体系不得引入新构建依赖。

## 决策

1. **暗色为首发一等形态**（O-4 收口）：[原型 §2.1](../25-ui-prototype.md) 的两列取值即实现契约，逐项落到 `apps/admin-web/src/styles/variables.css`（浅色 `:root` / 暗色 `html.dark`），由单测锁定。
2. **主题三态** `light | dark | auto`，**默认 `auto`**（跟随 `prefers-color-scheme` 并监听其变更，系统切换即时生效）；用户显式选择后固定，不被系统覆盖。旧持久化（只有 `darkMode` 布尔）按**显式模式**迁移，保证升级前后视觉零回归。
3. **语义色派生档按混色公式预计算为静态值**：浅色向白混色、暗色向黑混色，`dark-2` 各自反向，由单测按同一公式逐项校验（改基色漏改派生档即红）。**刻意不用 `color-mix()`**——实测构建期 CSS 管线（vite 8 / lightningcss）会**静默丢弃**无法静态求值的 `color-mix(in srgb, var(--x) 70%, #fff)` 声明，形成「开发态看着有效、构建产物回落组件库默认派生色」的假通过（见下「后果 / 验证」）。主色是运行时可选色，其派生档仍由 store 动态写入（`store/app.ts`，同一口径）。
4. **保留 Element Plus 结构边框五级**（extra-light 至 dark），不强行压到单一 `--fw-border`；差异在 `variables.css` 文件头如实登记。
5. **首帧上色脚本**（`index.html` 内联，先于应用脚本）：避免暗色用户看到浅色闪屏；该脚本与 store 同口径，键名 / 模式枚举 / 媒体查询串由单测断言同源。

## 备选方案

| 方案 | 优点 | 缺点 | 未选原因 |
|---|---|---|---|
| CSS 原生 `color-mix(in srgb, var(--x) 70%, #fff)` | 零依赖、零维护、改基色自动跟随 | **构建期管线（vite 8 / lightningcss）会丢弃无法静态求值的声明** → 开发态有效、产物回落组件库默认色；且需 `color-mix()` 浏览器支持 | 实测踩坑：产线静默错色比多维护几个常量危险得多 |
| SCSS / PostCSS 编译期派生 | 产物是静态值、可精确控制 | 新增构建依赖与管线；主色是**运行时**可切换的，JS 路径无论如何要有一份，形成两套派生 | 收益不足，维护面翻倍 |
| 引入前端色库（chroma / tinycolor） | 兼容性最好、算法可选 | 体积与依赖维护面（对抗 gzip 门禁） | 原生能力已覆盖目标浏览器 |
| 逐个手写派生色值（**采纳**） | 无新语法依赖、产物内联静态、全浏览器可用 | 6 色 × 6 档 × 2 主题 ≈ 72 个静态值，改基色需同步 | 由单测按混色公式逐项校验，漏改即红，成本可控 |
| 去掉 `auto`，只留显式两态 | 行为最简单、可预测 | 与系统偏好割裂，新用户首屏刺眼 | 体验倒退 |
| 把 EP 结构边框全部映射到 `--fw-border` | 「单一来源」最彻底 | 表格分隔线与输入框描边在暗色下几乎不可见 | 可用性优先于形式一致性 |

## 后果

**正面**：

- 令牌层成为唯一视觉契约——业务组件零颜色字面量由单测强制（`src/styles/__tests__/theme-tokens.test.ts`），换皮肤只改一个文件；
- 主色在两套主题下均取到正确对比度（暗色向黑混色 + 预设色各自的主题值）；
- 新用户默认跟随系统；系统主题切换无需刷新；
- 零新增依赖、零新增配置键、零后端改动。

**负面 / 代价**：

- 派生档是 72 个静态值：改任一语义基色都需同步重算（漏改会被单测按混色公式逐项标红，不会静默漂移）；
- `index.html` 需常驻一段前置上色脚本，构成 store 之外的**同一口径的第二份实现**；
- 显式选择与系统偏好之间存在「用户意图优先」的语义，需在 UI 上可回退到 auto（顶栏三态下拉提供）。

**验证与踩坑记录**：

- **构建管线会静默丢弃 `color-mix(..., var(...))`**：v1 实现用 `color-mix()` 派生，`vite build` 后产物里这些声明全部消失（无告警），暗色下回落成 Element Plus 自带派生色（基色与 EP 默认不同 → 视觉不一致）。改为静态值后复验产物逐项命中（`--el-color-success-light-3:#5dbd8a` / 暗色 `#26794a`、`--el-color-primary-light-3:#6d97ff` / `#4062b3`），并加一条「令牌文件不得出现 `color-mix(`」的护栏断言。
- **`smoke-mock` 不构建**：脚本只在 `dist` 已存在时跑体积门禁——改前端后若不先 `pnpm build`，门禁会在**旧产物**上通过（假绿）。本项的验证流程固定为：`pnpm build`（含 `vue-tsc`）→ 校验产线 CSS 取值 → `pnpm smoke`。

**缓解措施**：

- 单测双侧锁定：令牌文件按原型 §2.1 逐项 + 按混色公式逐项（浅色向白、暗色向黑、`dark-2` 反向）；
- 前置脚本与 store 的同源性由单测断言（键名 / 三模式串 / 媒体查询串 / 位置早于应用脚本），改一处漏另一处即红。
