# ADR-0007 · 数据库可切换靠「方言白名单 + 三库 CI 矩阵」

- 状态：已采纳
- 日期：2026-10-09
- 关联：PRD-002、[ADR-0002](./0002-orm-selection.md)

## 背景

1. 「ORM 支持多数据库」不等于「业务代码能切换」——方言差异（upsert 语法、JSON 函数、大小写敏感、全文检索）才是真正的坑。
2. 若不加约束，业务层会不知不觉写出只能在单一数据库运行的查询，切换承诺变成空头支票。
3. 需要一套可自动执行的机制，而不是靠文档与自觉。

## 决策

数据库可切换由三条硬性机制保障：

1. **方言白名单**：维护「可用能力清单」，禁止在业务层使用数据库特有语法；差异统一封装为适配器方法（`upsert()` / `jsonContains()` 等）。
2. **静态检查**：业务层出现原生 SQL 必须带方言标注（如 `@sql('mysql')`），否则 CI 失败。
3. **三库 CI 矩阵**：单元测试跑 SQLite，集成测试并行跑 MySQL 8 + PostgreSQL 15，任一失败即阻断合并。

切换步骤固化为：改 `.env` → `fw db:migrate` → `fw db:seed` → 跑集成测试。

## 备选方案

| 方案 | 优点 | 缺点 | 未选原因 |
|---|---|---|---|
| 仅依赖 ORM 抽象 | 零额外工作 | 方言泄漏无法发现，切换时集中爆雷 | 不可靠 |
| 每个数据库一套业务实现 | 可靠 | 维护成本翻倍，违背「一套代码」 | 排除 |
| 白名单 + 静态检查 + CI 矩阵 | 可自动验证、失败前置 | 需维护清单与 CI 资源（多两套库） | — |
| 只用一种数据库 | 最简单 | 直接违背核心卖点 | 排除 |

## 后果

**正面**：切换能力可被 CI 持续证明，而非口头承诺；方言问题在开发阶段暴露。

**负面 / 代价**：CI 需跑三套数据库，构建时间增加；白名单限制了部分高级特性（如 PG 的 jsonb 索引、MySQL 全文检索）。

**缓解措施**：本地单测用 SQLite 保证秒级反馈，双库集成只在 PR 与每日流水线执行；确需方言能力时走适配器方法并在三库验证；每半年复盘一次白名单，按实际需求增补。
