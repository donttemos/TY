# ADR-0010 · 可观测：先统一 traceId，M8 再引入 OpenTelemetry

- 状态：已采纳
- 日期：2026-10-09
- 关联：PRD-001、PRD-008、[运维手册](../60-deployment-ops.md)

## 背景

1. 排障的第一步是「用 traceId 串起一次请求」，这个能力 M1 就要有。
2. 完整的分布式追踪（span、采样、导出、后端存储）是重资产，小档部署不该被迫引入。
3. 但从单体演进到微服务后，没有标准追踪就无法定位跨服务问题。

## 决策

- **M1**：实现轻量链路 ID —— 中间件生成或透传 `X-Trace-Id`，写入异步上下文，贯穿日志、响应头与错误对象；日志为结构化 JSON。
- **M8**：引入 OpenTelemetry，traceId/spanId 标准化并导出 OTLP，覆盖 HTTP / DB / 缓存 / 队列；采样率可配，错误全采。
- traceId 字段命名与语义在 M1 就与 OTel 对齐（`traceId` / `spanId`），避免后期改名。

## 备选方案

| 方案 | 优点 | 缺点 | 未选原因 |
|---|---|---|---|
| 一开始就上 OpenTelemetry | 一步到位 | 小档部署被迫引入采集链路，违背 C1；早期收益低 | 过度前置 |
| 只做自定义 traceId，永不接入标准 | 简单 | 微服务阶段无法与网关/中间件生态打通 | 不满足 M8 |
| 分阶段：traceId → OTel | 早期零负担，后期可平滑升级 | 需保证字段语义前向兼容 | — |
| 依赖 APM 商业方案 | 开箱即用 | 成本高、绑定厂商 | 不符合自托管定位 |

## 后果

**正面**：小档零额外组件即可具备排障能力；M8 升级时日志与追踪字段无需改造。

**负面 / 代价**：M1–M7 期间没有 span 级耗时明细，跨服务性能问题定位较粗。

**缓解措施**：在此期间用慢查询日志、缓存指标、接口耗时直方图补足；M8 落地 OTel 时保持采样开销对 P95 ≤ 5ms（TC-NFR 用例约束）。
