## 1. 背景与目标

### 1.1 现状基线

M1–M12 交付后，框架已具备：三库抽象与 CI 矩阵、RBAC + 数据权限 + 审计（含 M12 六字段扩展）、缓存三防护与分布式锁、多租户（三源解析 + shared/dedicated 隔离 + fail-closed）、队列与分布式定时任务、配置中心热更、统一可观测契约（requestId/traceId、指标段、审计过滤）。

`tenants` 表已有 `plan` / `status` / `expireAt` 字段，但**不生效**：无套餐定义表、无配额表、无用量表、无生命周期状态机、无到期自动处置任务、无运营后台页面。框架当前能「跑多租户」，还不能「经营多租户」。

### 1.2 结构性缺口

| # | 缺口 | 现状 | 影响 |
|---|---|---|---|
| U-13-1 | 套餐/订阅无领域模型 | `tenants.plan` 为裸字符串，无版本、无快照 | 无法升级/降级，历史用量无法对账 |
| U-13-2 | 配额无执行 | 无 quota_definitions / tenant_quotas；无软/硬限额语义；无并发安全扣减 | 超额请求不被拒绝；并发下靠「先读后写」必然超发 |
| U-13-3 | 用量不可追溯 | 无 usage_events / usage_rollups；无幂等键 | 重复投递重复计量；汇总不可验证、不可重算 |
| U-13-4 | 生命周期无状态机 | `tenants.status` 无合法迁移表、无幂等到期任务 | 冻结/终止不作用于业务入口；任务重复执行产生双重副作用 |
| U-13-5 | 无运营端与账单 | 运营人员需直连数据库操作租户 | 日常运营不可行、不可审计 |
| U-13-6 | 构建不可复现 | Windows turbo os error 231、Prisma engine 平台绑定、无 devcontainer、文档命令未在干净环境验证 | 「本机能跑、CI 能跑、真机能跑」三不一致反复出现 |

### 1.3 产品目标

| # | 目标 | 衡量口径 |
|---|---|---|
| G13-1 | **可限额**：套餐定义、订阅与生效配额形成闭环，软限额/硬限额/仅统计三种语义可配置、可执行、可测试 | `smoke-saas-ops` 覆盖三种限额行为；并发逼近硬限额不超发 |
| G13-2 | **可计量**：用量事件幂等可追溯，汇总可核对可重算 | 重复提交同一事件不重复计量；rollup 可从 events 重建且逐窗一致 |
| G13-3 | **可运营**：租户五态生命周期由统一领域服务驱动，冻结/终止真实作用于业务入口 | 合法/非法迁移全有测试；冻结租户业务请求被拒绝（4031）且管理端仍可导出 |
| G13-4 | **可交付**：新开发者在干净环境按文档完成安装→生成→构建→测试 | 干净 checkout 冒烟脚本通过；工具链版本在 README/CI/容器三处一致 |
| G13-5 | **可验证**：发布建立在可信的验证矩阵之上 | 发布说明列明已验证拓扑、未验证拓扑（Redis Cluster 等）、回滚方法 |

### 1.4 非目标（不做）

- 在线支付网关对接、自动扣款、发票（NG11-1 延续；只做账单记录与计费规则快照）。
- 公有云托管运营（NG11-4；运营后台是自托管交付物）。
- Redis Cluster / 多节点故障切换 / 高负载压测承诺（主线 B 只划清边界，不做验证替代）。
- 自研 MQ / 注册中心 / 对象存储（NG11-3）。

## 3. 目标用户与使用场景

### 3.1 用户角色

| 角色 | 描述 | 核心诉求 |
|---|---|---|
| 平台运营人员 | 自托管该框架的 SaaS 运营方员工 | 不碰数据库完成套餐管理、订阅变更、租户冻结/恢复/注销、用量与账单查询 |
| 租户管理员 | 接入平台的客户企业管理员 | 查看本租户套餐、配额余量、用量明细；到期/冻结时得到明确提示与恢复路径 |
| 租户最终用户 | 客户企业内的普通使用者 | 超额时得到可理解的错误提示与升级指引，而非神秘 500 |
| 框架开发者 | 基于 TY 二次开发的工程师 | 干净环境按文档跑通；本地/CI/真机构建结果一致；故障可复现 |

### 3.2 关键场景

1. **新租户开通**：运营人员在管理端为租户选择套餐并创建订阅 → 系统写入订阅快照与生效配额 → 租户进入 `active`，得到明确初始配额。
2. **用量超限**：租户业务请求触发硬限额 → 请求被拒（4029，附升级指引）；软限额触发 → 放行并产生告警事件（走 M12 审计 + 通知渠道）。
3. **订阅到期**：到期定时任务（幂等）将租户置入 `grace` → 宽限期结束仍未续订 → 自动 `frozen` → 业务入口拒绝请求（4031），管理端仍可登录导出数据。
4. **套餐变更**：运营为租户升级套餐 → 新订阅生效，旧订阅留版本快照 → 历史用量与账单不被静默改写。
5. **租户注销**：运营发起终止 → 进入既定数据保留期 → 期满按策略导出/删除，全过程审计留痕。
6. **新成员入职**（主线 B）：开发者拉取干净 checkout → 按 Dev Container 指南 30 分钟内跑通「生成 → migrate → seed → 登录 → CRUD」。

## 6. 关键设计（摘要）

详细设计见配套《开发文档》（docs/47）。要点：

1. **套餐定义与生效配额分离**：套餐描述默认权益 → 订阅确定版本与期限 → 租户配额表达最终生效值。
2. **用量原始事件与汇总分离**：rollup 可随时从 events 重建；缓存中的余量只是加速视图。
3. **生命周期由领域服务独占**：控制器、定时任务不得直改 `tenants.status`；全部迁移走 `TenantLifecycleService` 并写审计。
4. **兼容期策略**：`tenants.plan/status/expireAt` 保留为派生只读列（由订阅/生命周期服务回写），设退役里程碑。
5. **验证边界声明**：Standalone Redis、双进程共享 Redis 与 Redis Cluster 的验证结论分开表述，不互相冒充。
