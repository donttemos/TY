# PRD-017 · TY Studio（本地可视化开发工作台）

> 里程碑：M17 ｜ 状态：**已发布 v0.8.0**（S1 只读工作台 / S2 设计器与 schema 安全写回 / S3 生成页与生成物指纹保护 / S4 AI 审查与 AI 建模已交付；**S5 部署中心、S6 轻量编辑器待做**）｜ 优先级：P1 ｜ 依赖：M6 生成器、M16（gen/deploy/verify 三条命令）｜ 负责人：donttemo ｜ 更新：2026-10-28

## 1. 定位

TY Studio 是**本地可视化开发工作台**，不是「CLI 的网页面板」，也不是在线 IDE。主路径：
项目 → 数据模型 → 业务生成 → 代码编辑 → 运行 → 部署。

它解决的问题只有一个：**开发者不必记住命令、不必满仓找配置文件、不必手写 Prisma Schema**。
CLI 继续作为底层引擎保留，终端用户与可视化用户走同一套实现。

## 2. 范围

**做**：项目识别与体检、数据模型设计器（含 schema 安全写回）、一键生成、运行与日志、部署中心、轻量代码编辑器。

**不做**：完整 IDE（LSP / 补全 / 多 tab / 调试器）、数据库客户端、在线改 schema 的云端版本、用户与权限（本地单用户）、把全部 CLI flag 搬成表单。

## 3. 六条铁律（复杂度与安全的总闸）

1. **文件是唯一权威，设计器只是视图**：每次操作前重读磁盘，不做内存缓存；用户在编辑器里改了 schema，回到设计器刷新即可看到。
2. **读＝文件，写＝受控通道**：只读信息（模型列表、`fw.gen.json`、`verify-report.json`）直接读文件；任何写操作必须经 CLI 子进程或写回内核，Studio 不复制业务规则。
3. **schema 块级重写**：只重建被编辑的 model 块，其余块逐字节保留——未改动模型里的注释、`@@index`、`@relation(onDelete:)` 一个字节不动。
4. **守门人是 Prisma**：写回前必须过 `prisma validate`；结构自检只做「早失败」；危险变更按 `gen/migration.ts` 的 blocked/confirm 分级；**永不自动执行迁移**。
5. **服务不可成为任意命令接口**：只监听 `127.0.0.1`、本机令牌（按项目持久化、可轮换）、动作白名单（前端传动作名与参数，不传命令）、路径限定在项目根内、校验 `Host`/`Origin`。
6. **Studio 与产品后台物理隔离**：Studio 是开发者本机工具、永不部署；后台是产品。两者互不依赖，由门禁固化（详见 §6）。

## 5. 关键设计（已定）

**schema 写回内核**（`packages/cli/src/studio/schema-doc.ts`，已实现并验证）：
切块（`model`/`enum`/`datasource`/`generator`/`other`，含行号范围）→ 只重建被编辑块 → 结构自检 → `prisma validate` → 备份 → 临时文件 + rename 原子替换。
字段属性保存**原始文本**（`attrs`），不做归一化——现网 `gen/schema-parser.ts` 是词法级、面向生成代码的，归一会丢 `onDelete`、索引排序等信息，绝不能用来往返写回。

**校验实现**：`prisma validate` 子进程（零新增依赖，与「CLI 是唯一引擎」一致）。临时校验文件写在 schema 同目录，否则 `.env` 解析失败会误报。

**编辑器**：CodeMirror 6，单文件，保存走备份 + 原子写；不做 LSP。

**服务与界面**：`node:http` + SSE，不引框架；界面复用仓库既有 Vue3 + Vite + Element Plus，独立包 `packages/studio-web`，构建产物由 Studio 服务静态托管（不需要第二个 dev server，CLI 运行时不依赖 Vue）。

## 6. 与后台管理平台的边界（铁律 6）

TY Studio 是**开发者本地工具**；`apps/admin-web` + 应用服务是**产品**。两者受众、运行位置、鉴权模型都不同，
必须物理与依赖双重隔离——混在一起会同时坏掉两边。

| 维度 | TY Studio | 后台管理平台（admin-web + 应用） |
|---|---|---|
| 使用者 | 开发者（本机） | 业务用户（多租户、多角色） |
| 运行位置 | 只在开发机 `127.0.0.1:4310`，**永不部署** | 随应用部署（5173 dev / 域名 prod） |
| 鉴权 | 本机令牌（按项目持久化，`--new-token` 轮换；无账号体系） | 登录 + JWT + RBAC + 审计 |
| 数据来源 | 项目文件（只读）+ 本地 CLI 子进程 | 数据库 + 后端 API |
| 写操作 | schema / 生成 / 部署（对项目） | 业务数据（对库） |
| 产物 | 由 CLI 内置页面提供 | 自己的构建产物，独立托管 |

**四条硬规则（已由 `scripts/check-studio-separation.mjs` 门禁，接入 CI）**：

- R1 Studio 源码不得依赖 `apps/**`——开发工具不拿产品应用当运行时依赖；
- R2 后台前端不得引用 Studio（`@fw/studio`、`fw studio`、`/api/schema/*`）；
- R3 部署产物（`deploy/**`）不得出现 Studio——它永远不该被部署到服务器；
- R4 Studio 端口（4310）不得出现在部署配置或后台代码里，避免被当成对外服务。

**允许的复用**：设计语言、CSS 变量这类视觉约定可以共享；**不允许**共享运行时（路由、鉴权 store、构建产物）。
`fw verify` 用 admin-web 跑浏览器用例是**验证产品**，不是把两者耦合——它只读产品页面，产品不知道 Studio 存在。

### S3 关系配置（2026-10-22）

**为什么关系必须由服务端生成**：Prisma 强制关系两端同时声明，只写子端会直接校验失败（P1012）。让界面各自拼写两端，必然出现「一端写了、一端漏了」的半成品。所以 `buildRelationEdits` 在服务端生成：子端外键（默认 `<to>Id`，默认可空）+ 关系字段（`@relation(fields: [...], references: [id])`），父端反向数组（`<from>s <From>[]`，**列表不能带 `?`**——`Product[]?` 是非法 schema，这条是写代码时踩到并修掉的）。
接口：`POST /api/schema/relation { from, to, required? }` → 返回 `edits` + 预览（与 preview 同构），界面再把 edits 并回草稿。

**diff 呈现修复**：早期用「只裁首尾」的简化 diff，两处分散修改时会把中间整段标成删+增（关系配置一次改两个模型，diff 从 3 行真实变更膨胀到 30 行）。已改用 `gen/writer` 的 LCS 实现，同一操作 diff 收敛到 9 行且只含真实新增。

**错误信息质量**：Prisma 在真错误前会打若干 `warn`（配置弃用）与环境提示，原先「失败原因」被这些噪声占据。执行器已改为**跳过噪声行、优先取带 Error / P1xxx 的行**。

**已知缺口**：不支持删除模型（会连带丢表与生成物，需专门的确认流程）；不支持自关联与多对多（多对多需要中间表，留待后续）；界面未做浏览器点击验收（本机 chromium 不可用），已验收的是：构建、托管、资源类型、真实数据的关系预览与真实 `prisma validate`。

### S4 生成物指纹保护（FR-17-14，2026-10-22）

**为什么不能等生成全部成功再写清单**：若清单只在后处理全绿后才落盘，一次 `prisma generate` / 迁移这类环境失败就会留下「文件已生成、却没有指纹」的状态——漂移检测永远回答「不知道」，用户改没改过无从判断。因此改为「文件写完即记录，校验失败随文件一起回滚」：

- `writePlan` 成功后立刻按磁盘内容算 sha256 写入 `fw.gen.json`；
- `verify` 失败 → 文件回滚 + 清单还原成生成前的**逐字节原文**；`migrate` / `seed` 失败 → 文件与指纹都保留（此时代码与 schema 是对的，回滚反而制造不一致）。

**指纹只增不减**：`mergeArtifactHashes` 只替换本次确实写过的路径。`--only=backend/frontend/seed` 局部重跑不会把其余产物的指纹抹成「未知」；被跳过的文件沿用旧指纹（不能拿用户改后的内容冒充生成基线）。`--only=frontend` 只刷新清单里已有模型的指纹、不新增条目——清单同时是接线事实源，凭空加条目会让 `check-gen-sync` 谎报已接线。

**生成前就能看见**：`modified` 与 `missing` 分开提示——合并成一句「会跳过」会让用户以为删掉的产物不会回来。`modified` 提示「默认跳过，`--force` 会覆盖并丢弃修改」；`missing` 提示「会重新创建」；老清单明说「无法判断」，不把未知当安全。dry-run 预览逐文件标注「你改过这份产物」。

**接口与界面**：`GET /api/gen/drift` → `{ ok, tracked, models: [{ model, files: [{ path, status }], affected }] }`（清单损坏按无指纹处理，不 500）；生成页按「已修改 / 已删除」分组列出（各前 6 个），仅当存在已修改文件时出现 `--force` 勾选。

**已知边界**：① 只追踪 `fw gen crud` 的产物（模块 / 前端 views / api / 种子），`app.module.ts` 与 `seed.ts` 的标记块由生成器全量重建，不记指纹；② 指纹是全文 sha256，换行符差异也算改动（宁可多报）；③ 老清单要跑一次生成才建立基线，此前只提示「无法判断」；④ 指纹路径**以后端应用根为基准**（前端为 `../admin-web/...`），与生成时的 cwd 无关——早期若按仓库根记录，需重跑一次生成重建基线。

### S4 AI 审查（FR-17-23，2026-10-22）

**为什么只审生成物**：全仓库扫会把业务代码、配置甚至密钥一起发出去，token 与费用也不可控。审查范围限定为 `fw.gen.json` 的产物 + `app.module.ts` / `seed.ts` 两个接线文件——这正是「生成器刚写出来、最可能出系统性错误」的部分。

**为什么不用 SDK**：只依赖 `POST {baseURL}/chat/completions`，DeepSeek、通义、自建网关、Ollama 改一个环境变量即可切换；少一层依赖，也避免 SDK 版本与供应商兼容问题。

**为什么 `--dry` 不需要密钥**：dry-run 的价值是「先看清哪些代码会出境」。把它挡在密钥之后，用户就只能盲发。dry-run 输出文件清单，配置齐全时额外显示目标地址与模型名。

**为什么不截断超大文件**：模型看到半截文件会给出错误结论（例如「缺少校验」其实在后半段），比不审更糟。超限一律跳过并在提示词里如实告知「审查不完整」，禁止据此推断没问题。

**安全**：密钥仅从环境变量读取（`FW_AI_API_KEY`，兼容 `OPENAI_API_KEY`），不写项目文件、不进 `fw.gen.json`、不回显；错误信息脱敏（401 只提示检查变量名）；审查只读，不写盘。

**接口**：`GET /api/review` → `{ configured, baseUrl, model }`；`POST /api/review { models? }` → 202 + jobId（复用 `JobManager`，命令由服务端拼装）。未配置直接 400，避免用户看到「任务失败」而不是「你少了环境变量」。

**已知边界**：① 不做自动修复（结论供人判断）；② 不做行号跳转（模型行号仅供参考）；③ 不缓存结论（代码一改就过期）；④ 审查质量取决于供应商模型，提示词只能约束格式与红线。

### Model Designer Agent 提示词（FR-17-24，2026-10-22）

**为什么单独成 Agent**：它的目标与 Code Review 相反——前者要「提出一个合理设计」，后者要「找出已有代码的缺陷」。复用同一份提示词会让模型一边设计一边自我审查，输出趋于保守且格式漂移；拆开后两者的输入、输出协议、重试策略都能各自演进。

**为什么输入也必须是 JSON**：上下文（schema 片段、既有模型、框架约定、生成器能力）如果塞进自然语言，模型无法区分「读过」与「猜的」。结构化输入让缺失项显式化——缺 `conventions` 就只能在 `assumptions` 里声明「未提供」，不能假装已读项目。

**为什么 `revise` 必须走 CAS + operations**：用户很可能已经在表格里改了 5 个字段，再说「加多图」。若 AI 整份重发，前 5 处修改会被静默覆盖。因此 `revise` 只允许输出 9 类增量操作，`base_revision` 不匹配直接 409；破坏性由后端按操作类型推导（不采信模型自报），确认后才进 Schema diff。

**为什么参数分两层**：`generation_profile` 是业务参数（分页、排序、权限码、种子数），属于草案、可编辑；`recommended_call_params` 是调用参数，只作建议——温度上限 0.3、输出 token 上限由编排层估算封顶。模型不得输出供应商、地址、密钥，出现即整份拒绝（防提示注入）。

**为什么先定提示词、暂不接代码**：契约（字段字典 + 异常矩阵 + 自检）是后续编辑器、校验器、Schema 写回的共同依据；先接代码会把契约固化在半成品实现里。接入顺序定为：只读生成 → 增量 diff → Schema 写回。

**文案与校验分离**：提示词只能约束模型「愿意」输出什么，真正保证格式的是后端 JSON Schema（缺必填/类型错/枚举越界一律拒绝并回灌一次），自检 D1~D8 再机器复核一遍。文档里的商品模块示例已用 `JSON.parse` 校验为合法 JSON。

### AI 建模只读闭环（FR-17-24 第一步，2026-10-22）

**接口**：`GET /api/model-draft` 回 `{ configured, context }`（数据库类型、模型名、约定说明、是否截断），不回 schema 全文；`POST /api/model-draft { requirement, mode?, baseRevision?, draft? }` 同步返回已校验草案（不走任务队列：一次调用 10~40s，前端有明确 loading 即可）。未配置密钥 400 `ai-not-configured`，版本冲突 409，模型输出不合法 400 `schema-invalid`（带 `issues` 路径），上游失败 502 `model-failed`。

**校验器手写、不引 ajv**：规则与 docs/51 字段字典一一对应（缺字段/类型/枚举/命名/关系引用/索引列/UI 混库/增量操作/revision/CAS/策略扫描），零新增依赖。为了防漂移，加了一条 `docs-sync` 测试：**把 docs/51 里的商品示例直接丢进校验器**，示例不合法即代表契约与实现已经分叉；同时检查 R1~R17 在文档与代码提示词中同时存在。

**重试策略落地**：首次 JSON 解析或校验失败，把最多 10 条「路径 + 原因 + 码」回灌，并回放上一次原始输出作为 assistant 消息，最多再调 1 次；出现供应商/密钥字段（`E_POLICY`）直接拒绝不重试；`baseRevision` 与草案不一致在调用前就挡掉，不浪费一次模型调用。

**上下文按出现率推断，不写死约定**：从 datasource 读数据库类型；已有模型取 `schema-doc` 解析结果；框架字段（id/tenantId/审计四件套/deletedAt）按「≥50% 模型都有」判定— 真实仓库里 `tenantId` 恒 0 的场景不会把租户字段硬塞给模型。schema 超 18k 字符截断并标注；schema 缺失则显式声明「未读取」。

**界面只读**：Studio 新增「AI 建模」页，展示假设、待确认问题、提示、迁移风险与原始 JSON；**没有**「保存到 schema」按钮——按文档第 6 节的顺序，草案要先过编辑器与 `prisma validate`，本轮不做。

**审查分片（2026-10-27）**：单次审查按 24KB 预算切片（`--chunk-kb` 可调，≥4KB），超大单文件按行切段并在段头标注行号偏移；逐片调用、单片失败不中断、多片结论按 `## 分片 i/n` 合并。实测 61KB → 3 片，首片 21KB 成功、后两片仍超时（判断为供应商排队，非体积），故把预算暴露为参数。另有 `--split=file`（逐文件：失败隔离、行号不跨段，代价是拆散跨文件因果）与 `--split=model`（同模型 controller/service/dto/seed 一包、组内装箱；接线文件在预算内**随组发送**，超过 3 个模型或装不下时单独成组并提示）。Studio 生成页提供同一组选项。多片结论按「文件名 + 行号」归并、严重级取高、建议去重后输出汇总；模型输出不符合 `[P0]` 格式时回退原文。

**草案缓存与增量（2026-10-27）**：最近一份草案存 `~/.fw/drafts/<项目哈希>.json`（原子写、上限 512KB），刷新/重开自动恢复；`POST /api/model-draft/revise` 把模型返回的 `operations` 应用到**当前草案**并返回字段级 diff，界面确认后才覆盖，未点名字段保留。破坏性变更（改类型/收窄可空/去唯一/删除）标红并计入 `destructive`；`revision` 由服务端按旧值 +1，不采信模型回填。

**草案 → 设计器（2026-10-23）**：`POST /api/model-draft/to-editor` 只做格式转换与约定补齐，返回与 `ModelView` 同构的模型；前端把它们并入本地草稿（没有 original 快照 → `collectEdits` 按新建提交），随后走既有预览/写入。关系字段只保留外键并提示用「＋关系」补两端；update/delete 不导入（避免误碰存量数据）。**这条链路仍然不写盘**，写 schema 必须经过设计器的风险分级与令牌确认。

**软修复与硬拒绝的边界**：缺 `generation_profile`、UI 布尔写成字符串、索引引用未列出的字段、关系定义不完整或目标不存在（丢弃关系、字段降级为普通外键）——后端修复并记 warning，面板单列「自动修正」；命名非法、关系目标不存在、破坏性变更未标记——直接拒绝。判据是「修完是否仍然是用户想要的那个模型结构」。

**已知边界**：① 草案不持久化，刷新即丢（下一步随编辑器一起落 `.fw/drafts/`）；② `revise` 后端已支持，但界面没有 diff 与操作确认，暂不暴露；③ 字段级 `D1~D10` 中「unsupported_features 与 models 交叉比对」只做了策略层，未做完整语义比对；④ 未抽独立 JSON Schema 文件（PRD §11 Q3）。

### AI 路由页面化（FR-17-25，2026-10-22）

**为什么密钥不写项目**：写进项目 `.env` 等于给密钥发了一张进版本库的单程票。改为用户级 `~/.fw/studio-ai.json`（目录 0700、文件 0600），与项目仓库完全解耦；`FW_STUDIO_AI_FILE` 可覆盖路径（测试与多环境用）。

**优先级与生效时机**：页面配置 > 环境变量 > 默认。每次请求现场读文件（`aiEnv()`），所以页面保存后立刻生效，不需要重启 `fw studio`——否则「填完了还得重启」会让用户以为没保存成功。命令行 `fw review` 也走同一份合并逻辑，页面配好即可在终端用。

**不回显**：`GET /api/ai-config` 只回 `configured / baseUrl / model / apiKeySet / source / file`；保存响应同样只回状态。页面密码框留空 = 不修改，想删则点「清除密钥」（`clearApiKey`），避免「空字符串把密钥冲掉」这类误操作。

**测试连接只打 `/models`**：不产生推理 token 费用，401 直接提示检查密钥，地址错误提示协议与路径；失败不落盘、不影响已保存配置。

**错误必须能定位**：模型调用失败时打印完整 `POST …/chat/completions`；诊断分两步（`/models` + 最小对话），404/401/429/400/超时各给结论。实测 Cline 的 `deepseek-chat` 会被拒（要求 `provider/model`），诊断直接给出 `deepseek/deepseek-chat` 的提示——这类「看起来像超时、实际是参数格式」的问题不能再让用户猜。

**模型名从地址取**：同一份 `/models` 结果去重排序后回给页面，输入框用 datalist 做「可选可填」——自建网关不实现 `/models` 时手填仍然可用，不能因为拿不到列表就堵死。打开已保存配置的实例会后台拉一次，避免每次手点。查列表失败返回 200 + `ok:false`：这是探测结果，不是请求错误。

**边界**：配置文件是明文（本机用户可读），不加密——加密需要主密钥，等于把问题挪个位置；能读你用户目录的人本来也能读环境变量。未做多套配置切换（一个 Studio 实例一套路由）。

### 本地令牌持久化（FR-17-26，2026-10-22）

**问题**：令牌每次启动随机生成，用户正在「AI 路由」里填配置时，只要服务重启过一次（改代码、换端口、重跑 `fw studio`），保存就 401，而报错只说「缺少或错误的 token」——看起来像填错了。

**改法**：令牌按项目持久化到 `~/.fw/studio-token.json`（目录 0700 / 文件 0600），项目路径做 sha256 前 16 位分桶（文件里不出现绝对路径）。优先级：显式参数 > `FW_STUDIO_TOKEN` > 已持久化 > 新生成并落盘。`--new-token` 强制轮换（会让其他已打开页面失效，属于显式动作）。

**边界**：令牌仍是随机强令牌（24 字节 base64url），只是生命周期从「一次启动」变成「按项目长期」，安全模型不变（仅 127.0.0.1 + Host/Origin 校验 + 所有 `/api/*` 校验）。文件损坏按空表处理并重建，绝不因为令牌文件坏了起不来。前端 401 文案改为「Studio 已重启或令牌已轮换：请用终端打印的最新地址重新打开」。
