# PRD-011 · SaaS 运营能力与生态扩展

> 里程碑：M11（v0.6.0–v0.8.0）｜ 状态：**草案**（2026-10-17）｜ 优先级：P1 ｜ 依赖：M1–M10 已交付能力（重点 M8 多租户 `@fw/tenant`、M9 `@fw/config-center`、M10 E-09 `@fw/storage` / E-12 事件面 / E-13 通知中心 / E-07 认证策略）｜ 负责人：donttemo ｜ 更新：2026-10-17
>
> 变更记录：2026-10-17 donttemo 起草——M1–M10 已把「单实例叙事」与「多实例一致性叙事」先后闭环（v0.5.0 已发布）。本次以「**产品能不能被运营**」的新视角复核，识别出四类结构性缺口，并据此提出九大方向共 42 项需求（S-01~S-42）：
> ① **运营缺口**——`tenants` 表已有 `plan` / `status` / `expireAt` 字段，但**无不生效**：无套餐定义、无配额、无用量统计、无计费、无生命周期动作（升级/降级/冻结/注销）、无运营后台。框架当前能「跑多租户」，但不能「经营多租户」——SaaS 化落地的第一道门槛。
> ② **生态缺口**——`templates/` 只有仓库内静态资产（api / codegen / admin），`fw new --template=x` 只认内置名；无插件注册机制、无远程模板市场、无版本与依赖解析、无社区贡献通道。G1「1 天骨架」只在框架自带模板范围内成立。
> ③ **驱动缺口**——「端口 + 多驱动 + `*_DRIVER` 枚举」范式已成熟（cache/queue/transport/config-center/storage 五处先例），但每个端口的驱动覆盖面与企业内网现状不匹配：配置中心只有 file/nacos、缓存只有 memory/redis、队列只有 memory/bullmq、存储只有 local/s3、认证只有 jwt/oauth2/apikey/session。企业落地时**第一句话往往是「我们用的是 Apollo / Kafka / OSS / 企业微信」**。
> ④ **工程化缺口**——生成器只覆盖单表 CRUD（无关系/前端/权限/i18n/测试生成、无 dry-run/diff/回滚）；可观测只有 Prometheus 文本端点散段（无标准指标命名收敛、无 Grafana 面板、无告警规则、无日志聚合）；安全合规有 OAuth2 与审计归档但缺「真机 IdP 实测、密钥轮换、密钥托管、合规导出」；开发体验有裸机与 1Panel 部署但**无 devcontainer / 可复现远程验证环境**，且两个已知工程债未清（根 `turbo run` 在本机 os error 231、Prisma engine 平台相关导致 Windows 产物不能上 Linux——后者直接影响「本机能跑、CI 能跑、真机能跑」三一致）。
>
> 与既有结论的衔接（重要）：
> - 81 号规划 §5「明确不做」中的 **Kafka 驱动**（O-5 结论）在本 PRD 中**改判为「做，但降档为 P3 按需」**——理由是 PRD-011 的语境已从「框架自身是否需要」变为「企业落地是否被驱动缺口卡住」，Kafka 是金融/政企落地的高频前置条件。改判需在 81 §5 与本文 §9 OQ-1 双向登记，本文所有驱动项统一记入 **OQ-1「驱动新增的准入判据」**。
> - NG2（不自研基础设施）/ NG4（不做低代码）/ NG5（不做营销页大屏）/ NG7（不做公有云托管运营）**仍然成立**，本 PRD 不越界；「运营后台」指的是**框架交付给你自托管**的租户运营控制台（属 NG7 的边界内：交付工具，不代运营）。
> - 「插件市场」需与 NG2/NG4 划清界限：**插件 = 可安装的代码与配置包，不是运行时解释的元数据**（ADR-0009 决策延续）。市场只是分发与版本解析通道，不引入运行时沙箱。

## 1. 背景与目标

### 1.1 已完成能力（基线）

M1–M10 交付后，框架具备：三库抽象与 CI 矩阵、RBAC + 数据权限四档 + 审计、缓存三防护、管理后台（动态路由/按钮级权限/TagsView/i18n 骨架/暗色模式三态）、CRUD 生成器、队列与分布式调度、多租户（三源解析 + shared/dedicated 隔离 + fail-closed）、transport 双驱动 + 链路追踪、配置中心热更与回滚（多实例一致）、任务中心三驱动、框架级 API 限流、SSE 事件面 + 站内信通知中心、对象存储端口、审计归档、前端 RUM。

一句话：**「一个团队搭一个系统」这条路已经走通，「一个平台运营很多个租户、并让外部生态参与进来」这条路还没开始修。**

### 1.2 四类缺口（评估结论）

| # | 缺口 | 现状证据 | 影响 |
|---|---|---|---|
| U-1 | **多租户不运营** | `tenants` 有 `plan`/`status`/`expireAt` 三列但无非空约束、无套餐表、无配额表、无用量表；`status` 无状态机、无到期自动处置任务；无任何 `billing`/`quota`/`usage` 端点与权限码 | 商用 SaaS 无法上线：不能限额、不能收费、不能止付、不能注销 |
| U-2 | **模板不可扩展** | `templates/` 为仓库内静态目录；`fw new --template=<内置名>` 无拉取/校验/版本语义；`@fw/cli` 无插件概念 | 社区贡献无法进入；每个团队自建脚手架只能 fork 仓库 |
| U-3 | **驱动面窄** | 五类端口合计 5+3+2+2+4 = 16 个驱动，缺企业内网主流选项（Apollo/Consul/etcd / KeyDB/Dragonfly / Kafka/RabbitMQ/NATS / OSS/MinIO/COS / LDAP/SAML/企业微信/钉钉） | 落地项目第一步就要自己写适配器，框架「可替换」承诺在企业内网打折 |
| U-4 | **工程化欠账** | 生成器无 `--dry-run`；观测无标准指标集与告警规则；无密钥托管与轮换；无 devcontainer；根 `turbo run` 本机 os error 231、Prisma engine 平台绑定 | 「1 天骨架」在陌生机器上仍要半天调环境；「本机过 CI 挂」类问题反复出现 |

### 1.3 目标

| # | 目标 | 衡量 |
|---|---|---|
| G11-1 | **可运营**：租户从开通到注销全生命周期有状态机、有配额、有账单、有告警；运营人员不碰数据库即可完成日常操作 | `smoke-saas-ops` 端到端：开通 → 用量超限拦截 → 升级 → 冻结 → 注销全流程通过；超限返回 4029 且带升级指引 |
| G11-2 | **可扩展**：第三方模板与插件可打包、发布、解析版本、一键安装，且安装失败可回滚 | `fw add <name>@<ver>` 从本地目录/HTTP 仓库/内置三种源安装成功；依赖冲突给可读错误；`--rollback` 还原 |
| G11-3 | **可替换**：每类端口的企业高频驱动「要么已实现、要么有明确不做的书面结论」 | 新增驱动全部具备双驱动单测 + 非法取值启动即失败 + 60 手册 §3 配置键登记 |
| G11-4 | **可交付**：任一台装了 Docker 的机器上 `devcontainer up` 后 30 分钟内跑通「生成 → migrate → seed → 登录 → CRUD」；三平台 engine 与根 turbo 债清零 | devcontainer 冒烟脚本；`turbo run build` 在 Windows/macOS/Linux 三平台零 os error |

### 1.4 衡量口径（本 PRD 完成时）

- 全部 P0 项（S-01~S-12）AC 勾选；P1 项 AC 勾选或明确降档并登记理由。
- 配置键从 97 增至 ≥ 130，全部经 `ENV_KEY_PATHS` 登记门禁校验。
- 数据字典新增表 ≥ 10 张（套餐 / 订阅 / 配额 / 用量 / 账单 / 通知渠道 / 通知模板 / 发送记录 / 插件登记 / 模板索引）。
- 新文档：`docs/42-saas-operations.md`（运营手册）、`docs/43-plugin-authoring.md`（插件与模板开发指南）、`docs/44-observability.md`（观测与告警）、ADR-0017（租户计费与配额模型）/ ADR-0018（插件分发与沙箱边界）/ ADR-0019（生成器模板解析）。

## 2. 范围

### 2.1 做（九大方向 · 四阶段）

**P0 — 运营地基（v0.6.0 主线）**

- **方向 1 多租户 SaaS 运营能力**（S-01~S-07）：套餐与订阅模型、配额定义与执行、用量采集与统计、租户生命周期状态机、计费与账单、运营后台租户管理、资源监控与告警。
- **方向 4 通知中心扩展**（S-19~S-22，前置最小集）：渠道抽象（邮件/短信/Webhook）+ 渠道配置 + 发送记录 + 失败重试。理由：配额告警、账单出账、冻结通知**全部依赖通知渠道**，不上渠道则运营闭环不成立。
- **方向 9 开发者体验**（S-38~S-40，前置最小集）：devcontainer + 根 turbo 修复 + Prisma engine 跨平台。理由：这三项是**全部后续开发的效率前置**，越早清越省。

**P1 — 生态与生成（v0.7.0 主线）**

- **方向 2 插件与模板市场**（S-08~S-13）：模板清单与版本、远程拉取、插件注册与生命周期、依赖解析、一键安装与回滚、社区贡献通道。
- **方向 5 代码生成增强**（S-23~S-28）：关系推导、前端页面、权限、i18n、测试生成、自定义模板、dry-run/diff/回滚、升级兼容。
- **方向 8 安全合规**（S-33~S-37）：真机 IdP 实测、API Key 轮换、密钥管理与托管、RBAC 细化、数据权限四档完善与合规导出。
- **方向 3 更多适配器 · 第一批**（S-14~S-18）：配置中心 Apollo/Consul/etcd、存储 OSS/COS/MinIO、认证 LDAP/OIDC/企业微信/钉钉（这四个认证驱动是**企业内网 SSO 的真实入口**，优先级高于队列类）。

**P2 — 规模化叙事（v0.8.0 候选）**

- **方向 6 微服务拆分演示**（S-29~S-32）：transport 远程化、服务发现、负载均衡、分布式事务边界。
- **方向 3 更多适配器 · 第二批**（S-16 队列 Kafka/RabbitMQ/NATS、S-15 缓存 Redis Cluster/KeyDB/Dragonfly）：与方向 7 的压测、方向 6 的拆分演示共用环境。
- **方向 7 可观测性告警**（S-31 并入、S-32~S-34 段）：Prometheus 标准指标集、Grafana 面板、告警规则、日志聚合、OTel 采样策略、RUM 多实例聚合。

**P3 — 体验与文档（按需穿插）**

- **方向 9 剩余项**（S-41 文档与教程体系、S-42 视频与最佳实践）。
- 方向 4 剩余渠道（钉钉/企业微信应用消息、短信备用通道）、方向 1 的账单 PDF/对账单。

### 2.2 不做（明确划界）

| # | 不做 | 理由 |
|---|---|---|
| NG11-1 | **在线支付网关对接**（微信支付/支付宝/Stripe 直连、自动扣款、发票开具） | 属业务与合规强耦合领域（资质、对账、退款流程），框架只交付**账单与计费规则引擎 + 支付回调接口位**；支付实现由落地项目自行接入 |
| NG11-2 | **运行时插件沙箱**（进程内解释第三方代码、热加载不受信插件） | 与 NG4 同源：插件是**安装期生效**的代码与配置包，需构建/重启；不做运行时解释器（ADR-0018） |
| NG11-3 | **自研基础设施**（自建 MQ/对象存储/注册中心） | NG2 不变；只做适配层 |
| NG11-4 | **公有云托管运营**（框架方代客户运营租户、SaaS 后台即服务） | NG7 不变；运营后台是**交付给客户自托管**的控制台 |
| NG11-5 | **营销页 / 数据大屏 / 低代码运行时** | NG5 / NG4 不变 |
| NG11-6 | **多云统一资源编排**（跨云 Terraform 抽象、成本优化调度） | 超出框架职责；K8s/Helm 模板已够 |
| NG11-7 | **完整 APM 产品替代**（自建 Trace 存储与查询 UI） | 已有 OTel 出口，链路存储与 UI 交给 Jaeger/Tempo；框架只保证埋点与采样策略正确 |

## 3. 用户故事 / 场景

**运营 / SaaS 负责人**

- 作为 SaaS 运营，我给客户开通一个「标准版」租户，配额（用户数 50 / API 调用 100 万次每月 / 存储 10GB）自动生效；客户用超了，系统按我配的策略拒绝或告警，而不是等我发现。
- 作为 SaaS 运营，客户月底续费前我打开运营后台，看到所有租户的用量、账单、即将到期清单，点两下就完成续费延期和套餐升级。
- 作为 SaaS 运营，客户欠费我不需要登录数据库改 `status`——在后台点「冻结」，该租户所有 API 立即返回可读的冻结提示，解冻后自动恢复。
- 作为 SaaS 运营，客户要注销，数据保留期到期后系统自动清理，全程有审计记录可回溯。

**落地项目开发者**

- 作为开发者，我拿到一份 `plugin.json` 就能把公司内部的「审批流插件」装进任意基于本框架的项目，不需要改框架源码。
- 作为开发者，`fw new my-erp --template=erp` 从公司私有模板仓库拉取骨架，版本锁定可复现；模板升级时 `fw upgrade` 给出 diff 让我逐处确认。
- 作为开发者，我用 `fw gen crud order --with=relations,frontend,i18n,tests --dry-run` 先看要生成什么，确认后落地；生成错了 `fw gen rollback --last` 一步还原。
- 作为开发者，我在公司机器上 `devcontainer up`，不需要装 Node/pnpm/Prisma 就能跑通全流程；Prisma engine 不再因为我在 Windows 开发而部署不到 Linux。

**运维 / 安全**

- 作为运维，我 `helm install` 后就拿到 Grafana 面板与告警规则，队列积压、限流拒绝、配额超限、账单异常都有现成规则，不用从零写 Prometheus 表达式。
- 作为安全负责人，我的 API Key 可以按周期轮换且有双活窗口；密钥不落配置文件，走 Vault/KMS；审计数据可按合规要求导出为标准格式。
- 作为架构师，我要把订单模块拆成独立服务，只改 `transport` 配置和部署清单，业务代码 diff = 0；拆分后链路追踪依然贯通，跨服务事务的边界在哪里有明确文档。

**生态贡献者**

- 作为社区贡献者，我按指南把模板打包发布，别人 `fw new --template=<我的模板>` 就能用；我的模板通过框架的模板冒烟脚本验证后才被索引收录。

## 4. 功能需求（FR）

> 编号 `S-xx`（SaaS & Ecosystem），与 `E-xx` / `L-*` / `R*-*` 不冲突。每项可独立验收；**关键约束**列必须在本项交付时逐条满足。

### 方向 1 · 多租户 SaaS 运营能力

| 编号 | 需求 | 关键约束 | 优先级 |
|---|---|---|---|
| S-01 | **套餐与订阅模型**：`plans`（套餐定义：编码/名称/版本/价格/周期/是否公开/排序）+ `plan_quotas`（套餐额度项）+ `tenant_subscriptions`（租户订阅：租户/套餐/周期/起止/状态/变更来源）。套餐支持「按量」「包年包月」「免费」三种计费模式 | 沿用 schema 无 `@relation` 约定，关联列裸 String；分派入参写库前过 `AuthService.assert*Ids`；`plans.code` 唯一且不可变（版本升级走新 code）；套餐变更只追加订阅记录，不原地改历史 | P0 |
| S-02 | **配额定义与执行**：`quota_definitions`（额度项字典：`key`/名称/单位/计量窗口 `none|day|month`/超限策略 `reject|warn`/是否硬限）+ `tenant_quotas`（租户当前生效额度，取套餐额度与租户覆盖值的较大优先级）。执行点：① 鉴权后中间件按 `key` 校验租户额度；② 业务侧声明式装饰器 `@Quota('user.count')` 在创建前校验存量 | **超限返回新错误码 `4029`（配额不足）+ 响应体带 `quotaKey`/`limit`/`used`/`planCode`/升级提示字段**（前端据此弹升级引导）；`warn` 策略不拦截但必进告警；配额检查默认 fail-closed（额度查不到即拒），与租户 fail-closed 同构；检查结果与用量计数分离（避免读放大） | P0 |
| S-03 | **用量采集与统计**：`usage_events`（原始事件：租户/额度 key/数量/时间/来源/幂等键）+ `usage_rollups`（按租户 × 额度 key × 窗口聚合：日/月）。采集方式：中间件自动计数（API 调用数）+ 业务显式上报（`UsageService.record()`，如存储字节数）+ 定时任务兜底重算 | 幂等键唯一约束防重复计数（E-13 先例：数据库唯一约束而非先查后写）；聚合任务复用 `@fw/queue` cron + 分布式锁（多副本单执行）；原始事件保留期可配（默认 90 天，超期归档，复用 E-10 归档范式）；统计查询走聚合表，**不在请求路径上做全表 count** | P0 |

## 6. 关键设计

### 6.1 计费与配额的模型取舍（ADR-0017）

**模型**：`plans`（套餐，含版本）→ `plan_quotas`（套餐额度项）→ `tenant_subscriptions`（租户订阅，历史追加）→ `tenant_quotas`（租户当前生效额度，派生/覆盖）→ `usage_events`（原始）→ `usage_rollups`（聚合）→ `bills`/`bill_items`（账单）。

**关键取舍**：

1. **额度与用量分离**——`tenant_quotas` 存「当前允许多少」，`usage_rollups` 存「已经用了多少」。检查配额时读两者并比对，**不遍历明细**。这使配额校验 O(1)。
2. **超限即时报错而非异步通知**——`reject` 策略在中间件层同步返回 `4029`（带升级指引），`warn` 策略放行但进告警。理由：同步拒绝才能真正防住滥用；异步通知只适合软性提醒。
3. **订阅历史追加而非原地改**——套餐升级/降级产生新订阅记录（旧记录标 `superseded`），保留完整计费可追溯性；`tenants.plan` 作为**派生缓存列**同步最新值（旧接口零回归）。
4. **出账幂等靠唯一约束**——`(tenant_id, period)` 唯一；重跑任务不重复出账（E-13/E-10 同款纪律）。
5. **不接支付**（NG11-1）——账单状态机留 `paid` 由外部回调写入；回调接口需签名 + 幂等。框架不碰钱。

**非目标澄清**：不做按秒计费、不做阶梯定价的复杂规则引擎（只支持「单价 × 数量」与「套餐内含额度 + 超量单价」两种）；不做多币种换算（币种字段保留但只支持单币种账期）。

### 6.2 通知中心的派发链路（在 E-13 之上扩展）

```
业务/事件源 ──► 通知意图（template + recipients + vars + channels）
                    │
                    ▼
            NotificationService.dispatch()
                    │  ① 解析模板（S-21 渲染 + 变量校验 + i18n）
                    │  ② 解析渠道（S-20 渠道配置 + 启用过滤 + 优先级）
                    │  ③ 写 notification_logs（状态 queued）
                    ▼
             @fw/queue 异步投递 ──► NotificationChannelPort.send()
                                          ├─ inapp  → 既有 notifications 表 + SSE（E-13 零回归）
                                          ├─ email  → SMTP 驱动
                                          ├─ sms    → 短信驱动
                                          └─ webhook→ HTTP POST（签名头 + 重试）
                    │
                    ▼
             成功 → 状态 sent ｜ 失败 → 指数退避重试 → 超限进死信（可查询 + 手动重发）
```

**关键取舍**：站内信从「唯一实现」降为「渠道之一」，但**表结构与端点保持不变**（E-13 零回归）；通知意图与渠道解耦，使新增渠道不改业务代码（G2 同款承诺）。

### 6.3 插件与模板的分发模型（ADR-0018）

- **清单驱动**：`fw-manifest.json` 是唯一契约；三种源解析后产同一结构；`fw-lock.json` 锁版本 + 内容哈希保证可复现。
- **安装 = 声明式装配**：插件声明「要注册哪个模块文件、追加哪些配置键、插入哪些 seed、声明哪个迁移目录」，由 CLI 执行。**没有任意脚本执行**（NG11-2）。
- **回滚 = 快照先行**：写入前快照全部受影响文件，任一步失败即还原；`--dry-run` 输出完整变更预览。
- **冲突检测前置**：路由前缀 / 权限码 / 配置键 / 表名四类冲突在安装前静态检测。
- **与 NG4 的边界**：插件在**安装期**作用于源码与配置，构建后即普通代码；不做运行时元数据解释。

### 6.4 生成器的模板指纹与三方合并（S-28 升级兼容）

生成产物头部写入指纹注释：

```ts
// @fw-generated { template: "crud-backend@2.1.0", hash: "sha256:<内容哈希>", generatedAt: "..." }
```

`fw gen upgrade` 时三方比对：
- **模板新版本产物**（新模板渲染结果）
- **原生成版本产物**（同指纹可从模板历史重渲染）
- **用户当前内容**（磁盘实际内容）

三者相同 → 静默跳过；仅用户改动 → 保留；仅模板变更 → 提示可更新；两者都改 → **冲突显式列出，让用户决策**（绝不自动覆盖用户改动）。模板历史版本随模板包携带（`templates/<name>/versions/`），保证可重渲染。

| **配置键爆炸** | 预估新增 ≥ 33 键，登记遗漏或语义重复风险高 | `ENV_KEY_PATHS` 门禁零例外（既有 env-registry 单测强制 schema 与注册表一致）；每阶段收尾跑一次键集核对；避免同义键（如通知重试与队列重试的参数要区分命名） |
| **敏感数据面扩大** | 新增渠道密钥、API Key、Vault token、租户库密钥集中出现 | 统一走 `SecretPort`（S-40）；所有敏感值加密落库 + 响应不回显 + 日志脱敏覆盖；新增安全自查项进 60 手册 |
| **环境依赖** | 真实 IdP（可容器化，风险低）、Kafka/RabbitMQ/NATS/K8s 集群（本机不可用） | S-38 用 Keycloak 容器规避；S-16 优先 NATS/RabbitMQ 单机容器可行，Kafka 需真实集群（与 E-05/E-11 环境依赖同批解决，到位即做）；环境不齐的项 AC 登记为「未执行 + 可复现命令」 |
| **兼容性承诺** | G2「业务代码零改动」是本框架的核心卖点，S-18/S-19/S-29 都直接押注它 | 每项 AC 显式含「调用方 diff = 0」或「既有冒烟零改动通过」；不满足即视为未完成而非「有差异可接受」 |
| **文档同步成本** | 48 项 × 5 处同步（60/数据字典/api-spec/README/CHANGELOG）是巨大的纪律负担 | 文档同步写进每项 AC；阶段收尾做一次文档一致性核对（复用 docs/95 的六维度方法论）；新文档不超过 4 篇，避免文档面自身膨胀 |
